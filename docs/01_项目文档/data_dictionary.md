### 表关系（星型模型）

```
                    dim_channel ──┐
                                  ├── dim_user ──┬── user_daily_snapshot   （1 : N，每人每天一行）
                    dim_version ──┘  (user_id)  ├── game_event_log         （1 : N，每人每次行为一行）
                                                └── user_game              （1 : N，每人每款游戏一行）
                    dim_position ──── hr_recruitment_data (position_id)
                    dim_game     ──── user_game          (appid)
```

事实表（N 端）记录「发生了什么」，维度表（1 端）描述「是谁、哪款游戏、哪个渠道」。

## 二、数据来源与设计动机（常被追问的点）

### 2.1 真实数据（ODS 层）

| 文件 | 体量 | 体检结论 |
|---|---|---|
| `data/raw/steam_user_game.csv` | 111 MB / 1,009,745 行 | 7,731 个用户、9,935 款游戏、**无空值**；但存在 **169,471 组重复的 `(user_id, appid)`**；`is_played` 恒为 1，无区分度 |
| `data/raw/steam_game_meta.csv` | 2.9 MB / 14,736 行 | `appid` 唯一无重复；`release_date` 是 `"1 Nov, 2000"` 这种英文格式，已解析为 ISO 日期 |

**已做的清洗动作：**
1. `(user_id, appid)` 去重，保留 `playtime_forever` 最大的一行 → 1,009,745 行 → **840,274 行**。
   *为什么必须去重：如果不去重，`SUM(playtime_forever)` 会把同一份时长算两遍，所有时长类指标全部失真。*
2. `release_date` 解析为 `YYYY-MM-DD` + 单独抽出 `release_year`（便于按年筛选且不破坏索引）。
3. `is_free` 的 `True/False` 字符串转成 `1/0`（SQLite 没有布尔类型）。

### 2.2 模拟数据（DIM/DWD 层）——「数据补全」而非「编造」

真实 Steam 数据**只有静态快照**，没有时间维度、没有埋点、没有付费流水，做不了留存率、漏斗、ARPU 这类游戏运营的核心指标。所以需要补全，但补全的每一层都挂在真实数据上：

| 模拟要素 | 挂钩的真实数据 | 目的 |
|---|---|---|
| 5,000 个 `user_id` | 从真实 7,731 人中**随机抽样** | 用户可回溯、可交叉验证，不是凭空捏造 |
| 用户活跃倾向 `engagement_q` | 该用户真实 `playtime_forever` 的**百分位** | 真实的重度玩家在模拟数据里留存也更好，数据内部自洽 |
| 运营游戏 `appid = 730` | 数据集中**覆盖率最高**的游戏（6,613/7,731 = 85.5% 的用户玩过） | 保证用户池与游戏的关联是真实的 |
| 用户价值分层 S/A/B/C | 真实游玩时长的分位（前 10% / 10-30% / 30-60% / 后 40%） | 支撑「分层用户对比」类分析 |

**回答模板：**
> 「这个项目的数据是『真实骨架 + 模拟血肉』。真实数据集给了我用户和游戏的关联关系，但缺少运营埋点。我没有去网上找一个假数据集，而是保留真实 user_id 和 appid，用真实游玩时长驱动模拟用户的活跃倾向，再按游戏行业真实规律（幂律留存衰减、标准充值档位、版本节奏、渠道质量差异）生成埋点数据。这样既解决了数据缺口，又保证了数据的内部一致性。」

### 2.3 为什么数据库里存了 5,000 用户，而真实池有 7,731 人？

`dim_user` 只装参与运营的 5,000 人；`user_game` 保留全部 7,731 人的真实记录，作为「大盘参照」。两者的交集是这 5,000 人——这让 Agent 有能力回答「我们的用户画像 vs Steam 大盘画像」这类对比问题。

## 三、字段字典

### 3.1 `dim_game` 游戏维度表

| 字段 | 类型 | 说明 | 示例 |
|---|---|---|---|
| `appid` | INTEGER PK | Steam 游戏唯一 ID | `730` |
| `game_name` | TEXT | 游戏名称 | `Counter-Strike 2` |
| `genres` | TEXT | 游戏类型，逗号分隔 | `Action,Free to Play` |
| `is_free` | INTEGER | 是否免费：1/0 | `1` |
| `release_date_raw` | TEXT | 原始日期字符串（保留溯源） | `21 Aug, 2012` |
| `release_date` | TEXT | 解析后的标准日期 | `2012-08-21` |
| `release_year` | INTEGER | 上线年份 | `2012` |
| `recommendations` | INTEGER | Steam 推荐数（热度代理指标） | `164426` |
| `categories` | TEXT | 玩法/功能标签，逗号分隔 | `Multi-player,PvP` |
| `publishers` | TEXT | 发行商 | `Valve` |

### 3.2 `user_game` 用户-游戏游玩明细表

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | TEXT PK① | 真实用户 ID，如 `User_00001` |
| `appid` | INTEGER PK② | 游戏 ID |
| `group_name` | TEXT | 原数据集自带分组 `Group_1`~`Group_10`（**与业务无关，做分析时不要用**） |
| `playtime_forever` | REAL | 累计游玩时长（分钟） |
| `playtime_normalized` | REAL | 对数归一化后的时长，消除量纲，跨游戏可比 |
| `is_played` | INTEGER | **恒为 1，无区分度**，不要用于筛选 |
| `playtime_user_deviation` | REAL | 相对该用户自身平均时长的偏离度（正=这款游戏他玩得比平时多） |
| `playtime_game_deviation` | REAL | 相对该游戏全体玩家平均时长的偏离度 |

> 复合主键 `(user_id, appid)` 且使用 `WITHOUT ROWID`，节省约 30% 存储空间。

### 3.3 `dim_channel` 渠道维度表

| 字段 | 类型 | 说明 |
|---|---|---|
| `channel_id` | INTEGER PK | 渠道编号 1~6 |
| `channel_name` | TEXT | 自然量 / 抖音买量 / 腾讯广告 / 应用商店推荐 / KOL主播导量 / 老玩家邀请 |
| `channel_type` | TEXT | 免费 / 买量 / 联运 / 社交裂变 |
| `cost_per_user` | REAL | **单个注册用户的获取成本（元）**，自然量为 0 |

> `cost_per_user` 是渠道分析的关键：只有结合 LTV 才能算 ROI。设计占比约为 22% / 24% / 18% / 16% / 12% / 8%。

### 3.4 `dim_version` 版本维度表

| 字段 | 类型 | 说明 |
|---|---|---|
| `version_id` | TEXT PK | `v1.9.0` / `v2.0.0` |
| `version_name` | TEXT | 夏日行动版本 / 竞技新纪元（2.0 资料片） |
| `release_time` | TEXT | 上线时刻，如 `2026-09-05 10:00:00` |
| `release_date` | TEXT | 上线日期，用于按天 JOIN |
| `version_type` | TEXT | 大版本 |
| `main_features` | TEXT | 核心更新内容（可作为 LLM 生成洞察的背景知识） |

### 3.5 `dim_user` 用户维度表

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | TEXT PK | 真实用户 ID |
| `channel_id` | INTEGER FK | 关联 `dim_channel` |
| `register_time` | TEXT | 注册时刻 `YYYY-MM-DD HH:MM:SS` |
| `register_date` | TEXT | 注册日期（**冗余列**，避免每次用 `date()` 函数导致索引失效） |
| `user_group` | TEXT | 价值分层 S / A / B / C |
| `engagement_q` | REAL | 活跃倾向系数（1.0 = 平均），**由真实游玩时长映射，仅供生成使用，分析时不用** |
| `real_game_cnt` | INTEGER | 真实玩过的游戏数 |
| `real_playtime_total` | REAL | 真实累计游玩时长（分钟） |
| `real_playtime_main` | REAL | 在运营游戏（appid=730）上的真实游玩时长 |
| `country` | TEXT | 中国大陆 / 中国港澳台 / 东南亚 / 北美 / 其他 |
| `device_os` | TEXT | iOS / Android |

### 3.6 `game_event_log` 行为事件日志（核心事实表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `event_id` | INTEGER PK | 事件 ID，按时间排序后连续编号 |
| `user_id` | TEXT | 用户 ID |
| `appid` | INTEGER | 游戏 ID（统一为 730） |
| `event_time` | TEXT | 事件时刻 `YYYY-MM-DD HH:MM:SS` |
| `event_date` | TEXT | 事件日期（**冗余列**，命中索引的关键） |
| `event_name` | TEXT | 见下方事件字典 |
| `event_value` | REAL | 仅「充值」事件有值（金额，元），其余为 NULL |

**事件字典（共 8 种，101,668 条）：**

| `event_name` | 条数 | 占比 | 含义 |
|---|---|---|---|
| `局内对战` | 53,620 | 52.7% | 完成一局对战，核心活跃行为 |
| `登录` | 28,994 | 28.5% | **每个活跃日恰好一条**，是活跃口径的唯一依据 |
| `注册` | 5,000 | 4.9% | 用户注册，每人一条 |
| `新手引导_步骤1` | 4,755 | 4.7% | 引导漏斗第 1 步 |
| `新手引导_步骤2` | 3,698 | 3.6% | 引导漏斗第 2 步 |
| `流失预警` | 2,511 | 2.5% | 用户最后一次活跃当天由风控模型打标（连续 7 天未登录判定流失） |
| `新手引导_步骤3` | 2,169 | 2.1% | 引导漏斗第 3 步 |
| `充值` | 921 | 0.9% | 付费事件，`event_value` = 金额 |

### 3.7 `user_daily_snapshot` 每日活跃与付费快照

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | TEXT PK① | 用户 ID |
| `date` | TEXT PK② | 日期 `YYYY-MM-DD` |
| `is_active` | INTEGER | 1 = 当日有登录；0 = 当日未活跃 |
| `revenue` | REAL | 当日付费金额（元），未付费为 0 |

> **这是稠密表**：用户从注册日到数据截止日，每天一行（217,750 行）。
> 为什么不只存活跃记录？留存率的分母是「该日全部新增用户」，稠密表让「某日新增用户在第 N 天是否活跃」直接 LEFT JOIN 即可，SQL 简单且不易写错。

### 3.8 `dim_position` / `hr_recruitment_data` 招聘表

`dim_position`：`position_id`、`position_name`、`department`、`headcount`（招聘人数）、`city`。共 8 个岗位（研发 3 / 运营 1 / 市场 1 / 策划 1 / HR 1 / 美术 1）。

`hr_recruitment_data`（**漏斗型事件表**：候选人每通过一个环节产生一行）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `candidate_id` | TEXT | 候选人 ID，如 `C00001` |
| `position_id` | TEXT FK | 应聘岗位 |
| `apply_time` | TEXT | 投递时间 |
| `interview_stage` | TEXT | `简历初筛` / `一面` / `二面` / `Offer` |
| `stage_index` | INTEGER | 环节序号 1~4（避免每次用 CASE WHEN 排序） |
| `stage_time` | TEXT | 进入该环节的时间 |
| `source_channel` | TEXT | 内推 / 官网投递 / BOSS直聘 / 猎头 / 校园招聘 |

**招聘漏斗实际分布：** 简历初筛 1,200（100%）→ 一面 364（30.3%）→ 二面 188（15.7%）→ Offer 102（8.5%）。

## 四、指标口径即预警（做分析前必读）

| 风险点 | 说明 |
|---|---|
| `is_played` 全为 1 | 原数据无区分度，**不要**用 `WHERE is_played = 1` 筛选 |
| `group_name` | 原数据集的随机分组，**与业务无关**，不代表渠道或用户分层 |
| **活跃口径唯一来源** | `user_daily_snapshot.is_active = 1` ⇔ 当天有 `登录` 事件（已校验 0 条不一致，见建库脚本验收报告第 3 项）。**不要用 `局内对战` 判断活跃**，那会漏掉只登录未开局的用户 |
| MAU 必须用滚动窗口 | 「近 30 天去重活跃用户」才有意义。若把 90 天全窗口去重活跃用户当 MAU，几乎所有注册用户都会被算进来（因为每人注册当天必然活跃），指标会虚高到 5,000 |
| 新增用户口径 | 以 `dim_user.register_date` 为准，每人一条记录，天然去重 |
| 留存分母要剔除数据不完整的人 | 算 D1 时，`register_date` 不能晚于 `数据截止日 - 1`，否则用户还没到第 2 天。**这是最容易算错的地方** |
| 日期截断偏差 | 招聘表最后几天投递的候选人漏斗还没走完，会被低估。分析时要么剔除最近 7 天，要么显式说明 |
| `event_value` | 只有 `充值` 事件非空，做其他事件分析时要忽略该字段 |
| 金额一致性 | `user_daily_snapshot.revenue` 合计 = `充值` 事件金额合计 = 97,548.00 元（已校验通过） |

## 五、索引设计

| 索引名 | 表 | 字段 | 服务的查询场景 |
|---|---|---|---|
| `idx_event_date_name` | `game_event_log` | `(event_date, event_name)` | 某天某事件的用户集合（留存、漏斗） |
| `idx_event_user_time` | `game_event_log` | `(user_id, event_time)` | 单用户行为路径下钻 |
| `idx_event_name_date_user` | `game_event_log` | `(event_name, event_date, user_id)` | 漏斗锚点查询，**覆盖索引**免回表 |
| `idx_snapshot_date_active` | `user_daily_snapshot` | `(date, is_active)` | DAU 按日扫描、留存按日过滤 |
| `idx_hr_position_apply` | `hr_recruitment_data` | `(position_id, apply_time)` | 分岗位漏斗 |
| `idx_hr_candidate` | `hr_recruitment_data` | `(candidate_id)` | 候选人下钻 |
| `idx_hr_stage` | `hr_recruitment_data` | `(interview_stage, stage_index)` | 环节漏斗排序 |
| `idx_dim_user_register_date` | `dim_user` | `(register_date)` | 新增用户按日聚合 |
| `idx_dim_user_channel` | `dim_user` | `(channel_id)` | 渠道分群 |
| `idx_user_game_appid` | `user_game` | `(appid)` | 按游戏反查玩家 |
| （隐式） | `user_daily_snapshot` | 主键 `(user_id, date)` | 按用户查每日明细 |
| （隐式） | `user_game` | 主键 `(user_id, appid)` | 用户-游戏定位 |

**设计原则：**
- **最左前缀**：`user_game` 主键是 `(user_id, appid)`，最左是 `user_id`，所以「按 appid 反查」必须单独建索引。
- **不重复建索引**：`user_daily_snapshot` 主键已提供「按用户查」的索引，不再重复建 `(user_id, date)`，避免写放大。
- **建索引时机**：`scripts/build_database.py` 严格按「建表 → 批量导数 → 建索引 → ANALYZE」执行。先有索引再导数会慢 3~5 倍（每插一行都要维护 B+ 树）。
- **ANALYZE**：不跑 `ANALYZE` 就没有列的数据分布统计，优化器可能选错执行计划。

## 六、模拟数据的关键业务假设（可被追问）

### 6.1 留存率模型：幂律衰减

```
P(第 d 天活跃) = D1 × d^(-α) × 用户活跃倾向 × 渠道质量系数 × 版本队列系数
其中 D1 = 0.38（基准次日留存），α = 0.44（衰减指数）
```

幂律衰减是留存曲线的经典经验规律：前期陡降、后期趋平（长尾）。参数代入可得理论值 D7 ≈ 16.1%、D30 ≈ 8.5%，与实测 **D1 = 39.2%、D7 = 16.5%、D30 = 8.9%** 吻合。

用户每天的活跃判断是**独立伯努利试验**（简化假设），因此不模拟「连续多天登录」的簇聚效应。

### 6.2 渠道质量系数（仅用于生成，**不入库**）

| 渠道 | 留存系数 |
|---|---|
| 老玩家邀请 | 1.15 |
| 自然量 | 1.10 |
| KOL主播导量 | 1.00 |
| 应用商店推荐 | 0.95 |
| 腾讯广告 | 0.90 |
| 抖音买量 | 0.85 |

> **为什么不能入库？** 如果把「渠道质量系数」写进表里，那分析「渠道留存差异」就变成了用答案验证答案。这个系数必须只活在生成脚本里，分析时要从数据里重新算出来。

### 6.3 付费模型

- 付费用户比例 5.30%（265/5,000 人）
- 付费笔数 = 1 + 泊松(2.4)，均值约 3.4 笔
- 金额从国内手游标准档位 `[6, 18, 30, 68, 98, 198, 328, 648]` 加权抽样
- 实测：总流水 **97,548 元**，ARPPU **368 元**，ARPU **19.5 元**（90 天口径）

### 6.4 版本节奏

| 版本 | 上线日 | 效果 |
|---|---|---|
| v1.9.0 夏日行动 | 2026-07-15 | 版本热度脉冲（当天活跃 ×1.40，之后 5 天递减） |
| v2.0.0 竞技新纪元 | 2026-09-05 | 同上 + **新增用户留存质量 ×1.25** |

实测验证：DAU 最高的一天正是 **2026-09-05（655）**，其次是 09-06（556），版本热度已正确落入数据。

### 6.5 其他假设

- 事件时刻按用户作息分布抽样，19:00–23:00 为高峰，03:00–05:00 最低
- 注册量：大盘线性增长 + 周末 ×1.25 + 版本上线脉冲
- 招聘投递：工作日 ×1.15，周末 ×0.55

## 七、埋入的业务真值（Agent 评测的「标准答案」）

模拟数据里刻意埋入了几条**已知结论**，Phase 5 可以用它们来检验 Agent 给出的分析结论是否正确——这是模拟数据相比真实数据的一个独特优势。

## 八、已知限制（主动暴露，是加分项）

1. **单游戏口径**：模拟运营数据只有一款游戏（appid=730），因此不存在「多游戏横向对比」的场景。真实发行商会有多个项目，本项目为了聚焦指标链路做了简化。
2. **活跃独立性假设**：每日活跃概率独立抽样，未模拟「玩家长草—回流」的周期性行为。真实数据中回流用户会带来 DAU 的小幅波动。
3. **无归因数据**：没有广告曝光、点击等前端数据，因此无法做完整的「曝光→点击→注册→付费」全链路归因，只有注册后的行为。
4. **付费行为简化**：付费时点在活跃日内随机分布，未模拟「付费后留存提升」的反向影响（真实数据中付费用户留存显著更高）。
5. **招聘数据截断**：最后几天投递的候选人漏斗未走完，Phase 5 评测时需注意。
6. **数据体积**：106.9 MB，其中 84 万行真实 Steam 明细占了主要空间。如果只需要跑通 Agent 链路，可以只加载 6 张模拟表（约 20 MB）。

## 九、复现命令

```bash
# 1) 安装依赖
pip install -r requirements.txt

# 2) 生成模拟运营数据（固定随机种子，结果可复现）
python scripts/generate_mock_data.py

# 3) 建库：建表 → 导数 → 建索引 → ANALYZE → 数据验收
python scripts/build_database.py
```

建库脚本跑完会自动输出一份**数据验收报告**，包含：各表行数、时间范围、两项一致性校验、版本前后留存对比抽检、执行计划验证、数据库体积。
