# 产品说明文档 · PRD（Product Requirements Document）

> 面向首次接触本项目的人：**这个产品解决什么问题、给谁用、凭什么可信、怎么验证它有效**。
> 技术实现细节不在这里展开，见《文件清单说明》与《测试复盘记录》。

---

## 一、一句话定位

把游戏运营每天要问的「数据问题」变成「点开即问、答案必须能溯源」的对话式分析入口，
**用语义层 + 规则护栏消除大模型编造数据的风险**，而不是靠提示词祈祷它别算错。

---

## 二、目标用户与核心场景

| 用户 | 角色 | 核心诉求 | 现在的痛点 |
| --- | --- | --- | --- |
| 游戏运营（主） | 版本、活动、渠道、数值运营 | 快速验证「上线后留存变好了吗」「这次活动值不值」 | 不会写 SQL；每次取数要排队等数据分析师；口径常被理解错 |
| 数据分析师（被赋能） | 取数支持 | 把重复性取数甩给 Agent，专注结论 | 大量时间耗在「同口径不同问法」的重复取数上 |
| 数据/算法工程师（被复用） | 指标平台建设 | 有一套可复用的「口径 + SQL 模板」资产 | 每个报表各写各的，口径散落 |

典型问法（来自评测集 31 条用例的实际场景）：

- 「最近 7 天的日活怎么样？」→ 映射 `dau`
- 「v2.0.0 上线后新用户留存变好了吗？」→ 映射 `version_retention`
- 「这次活动付费率比上周如何？」→ 映射 `payment_rate`

场景本质都可以归成同一类：**运营在决策前，要一个「可信、可追溯」的答案**。

---

## 三、问题定义与现状

### 3.1 这个领域已有的「通用方案」为什么不够

主流的对话式取数方案让大模型**直接生成 SQL**。它有两个致命问题：

1. **口径不可控**：同样「留存率」，模型可能随机理解成 D1 / D7 / D30，
   甚至自己发明一个没定义过口径的数字。
2. **幻觉无法拦截**：模型可能跳过取数、凭训练记忆答一个「像那么回事」的数字，
   而产品侧到「错了那一步」之前没有任何防线。

### 3.2 本产品的解法

**把模型的职责边界钉死在「语义映射」上**：

```
用户问题 ──► LLM 只做一件事：识别出 metric_id + 参数
               （例如 retention_rate + {day_n: 7}）
                    │
                    ▼
        程序按指标注册表的预审 SQL 模板填充参数 ──► 查库 ──► 答案
              （SQL 永远由程序生成，模型碰不到）
```

配套四层防线 + 一层答案溯源（详见下），把「幻觉」从架构上掐掉，而不是用提示词去赌。

## 四、核心产品能力

### 4.1 五条硬约束（产品承诺）

| # | 承诺 | 说了什么 |
| --- | --- | --- |
| ① | **LLM 不写 SQL** | 模型只输出指标 ID 和参数，SQL 由程序按模板生成 |
| ② | **SQL 只读且受控** | 仅 SELECT；表名单/模板/参数白名单、只读连接、行数上限、超时中断 |
| ③ | **结果双份输出** | 文本喂模型、结构化数据喂前端画图，两条路各走各的 |
| ④ | **重大决策人工确认** | 投放预算/版本调优/留存策略建议，强制「复核人 + 勾选 + 审计日志」 |
| ⑤ | **答案逐数字溯源** | 答案里每个数字必须能映射回本次查询结果；映射不上的拦截或标注 |

### 4.2 数据资产（12 个标准指标）

按「活跃 / 留存 / 增长 / 商业化 / 渠道 / 版本」六类组织：

| 类 | 指标 |
| --- | --- |
| 活跃 | DAU、MAU（滚动 30 天）、用户粘性 DAU/MAU |
| 留存 | 留存率（D1/D7/D30）、新手引导漏斗 |
| 增长 | 新增用户数 |
| 商业化 | 付费转化率、ARPU、ARPPU、LTV |
| 渠道 / 版本 | 渠道留存对比、版本前后新用户留存对比 |

口径、参数、来源表、SQL 模板全部固化在 `metrics_registry.json`（单一事实来源），
彻底解决「同样叫留存率、各算各的」的口径混乱。

### 4.3 接入能力（数据集级）

不止一套写死的数据：支持上传 CSV 自动建表 → 推断列语义角色（9 类）→ 生成指标草稿 →
人工复审后启用。**把一个新游戏接进来，从「开发排期」变成「运营自助」**。

## 五、为什么答案可信（产品信任设计）

这是本产品区别于普通 LLM 套壳的核心，也是评审者最该细看的部分：

- **第五层「逐数字溯源」**：把回答里**每一个数字**反向映射到本次查询结果集——
  全部找得到 → 原样给；少量找不到（≤1/3）→ 回答照给、末尾标注哪几个没出处；
  超过 1/3 → 判定疑似编造，**拦截整条回答**。宁可不给数字，也不给假数字。
- **为什么需要这一层**（真实事故逼出来的）：前四层都在 SQL 出口，隐含假设
  「模型一定会去查」。实测备用模型会**跳过全部工具、凭记忆答「日活 100,000」**，
  前四层对它完全无感。防线必须跟着数据流走，补在答案出口。
- **判据的口径演进**：第一版只问「有没有取过数」，于是「查了 1 次 DAU、又编了 5 个
  留存率」能混过去；升级为「逐数字溯源」后，这种混编会被拦下。

## 七、缺口与后续演进（已知边界）

产品向视角，诚实列出还不成立的事：

1. **没有真实业务用户**：场景是我模拟运营提炼的，价值验证是「方法论跑通 + 可复核证据」，
   不是真实 DAU/留存。接入真实业务前，第五层判据的参数（溯源阈值、拦截档位）需按真实数据校准。
2. **数据不接实时源**：当前是 CSV/批处理 + 内置数据。架构上「接数据源」只换 `FROM` 来源，
   本产品的技术主张在语义层，不在连接器层——这是有意的取舍。
3. **无星期/无行业基准**：提及相关因素只能写「可能与日历/行业因素有关，需外部数据验证」，
   这是对「不编造」承诺的诚实执行。
4. **单次成本未面向上游核算**：有 token 记账与评测 token 口径，但还没输出「单问 USD/元」的
   单位经济视图 —— 这是商业化上线前要补的。
5. **多 Agent / 多轮记忆**：当前是带上下文的单 Agent，未做多智能体编排与长期记忆。

## 八、产品定位小结

一句话面向不同角色：
- 对运营 —— **放弃 SQL，拿到敢用来做决策的数字**；
- 对数据团队 —— **口径与模板资产化，可复用、可审计**；
- 对技术评审 —— **大模型不能编数字，是一条可验证的工程承诺，不是一句提示词**。
