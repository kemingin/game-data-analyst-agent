一、项目全景
================================================================================

1.1 这是什么项目
--------------------------------------------------------------------------------
一个面向游戏运营团队的自然语言数据分析 Agent。运营同学用中文提问（比如
「次留是多少」「v2.0.0 上线后留存变好了吗」），Agent 自动完成：
    理解问题 → 映射到标准指标 → 生成 SQL → 安全校验 → 执行 → 解读结果 → 输出结论

但它不是我拍脑袋想出来的玩具。设计前先对齐了「游戏公司数据分析产品经理」
这个岗位的真实工作场景：运营每天要看的其实就是那十几个核心指标，痛点不是
「查不到数」，而是「口径不统一」「新人不会写 SQL」「拿到数看不懂」。

1.2 为什么这个项目适合作为求职作品
--------------------------------------------------------------------------------
它同时展示了三个岗位能力，这是普通"数据看板"作品做不到的：
    · 数据工程能力 —— 90 天真实量级的模拟数仓、星型模型、索引优化
    · 数据产品能力 —— 指标语义层（把口径变成可治理的资产）
    · AI 应用能力 —— 手搓 ReAct Agent、Function Calling、多供应商容错
    ★ Phase 6 又补上了第四个：**成本意识与可观测性** —— 把 token 账单
      拆成固定开销 / 可变开销、把缓存命中率做成指标，而不是"感觉挺贵的"。

1.3 分层架构（这是整个项目的主心骨）
--------------------------------------------------------------------------------
    ┌─────────────────────────────────────────┐
    │  前端层    Streamlit + Plotly（Phase 4） │  ← 给人看的
    ├─────────────────────────────────────────┤
    │  Agent 层   ReAct 循环 / Tools / Prompt  │  ← 决策与调度
    ├─────────────────────────────────────────┤
    │  指标语义层  注册表 + SQL 生成 + 校验 + 执行 │  ← 核心创新点
    ├─────────────────────────────────────────┤
    │  数据层    SQLite（9 张表 / 118 万行）     │  ← 事实来源
    └─────────────────────────────────────────┘
    ┌─────────────────────────────────────────┐
    │  评测体系  双路径对账 + 四档数字分类      │  ← 证明它真的好用
    │            （Phase 5 建立，Phase 6 扩到 31 条）│
    └─────────────────────────────────────────┘

★ 设计要点：这个架构最大的特点是「职责收窄」。每一层只做一件事，尤其是
  把 LLM 的职责从「写 SQL」收窄成「做分类 + 抽参数」，是整个项目准确率和
  安全性的根基。见 1.4。

1.4 五条硬约束（写进项目规范，不可违反）
--------------------------------------------------------------------------------
① LLM 不直接生成 SQL
   LLM 只负责「用户问题 → metric_id + 参数」，SQL 由程序按预审模板填充生成。
   原因：LLM 写 SQL 会同时踩三个坑——幻觉表名字段名、口径漂移、安全风险。

② SQL 只允许 SELECT
   双保险：执行层用只读连接打开数据库（写操作在驱动层就被拒），
   校验层再强制 SELECT 开头 + 表白名单 + 强制 LIMIT。

③ 参数不拼接，一律占位符绑定
   从机制上杜绝 SQL 注入，而不是靠"过滤危险字符"这种黑名单思路。

④ 重大决策类分析必须留人工确认节点
   比如「版本调优建议」这种会影响线上决策的输出，Agent 必须明确提示
   「需人工复核后执行」，不能直接下结论。

⑤ 回答里的数字必须能溯源（★ Phase 6 新增，见 7.4）
   本轮没有任何一次成功的 query_metric、却报出了数据型数字 → 判定为疑似编造，
   强制重新取数；补救用尽仍在编造，就拦截整条回答，宁可不给数字也不给假数字。
   ★ 为什么要加这一条：前四条全在 SQL 出口，默认「模型一定会去查」。
     真机告诉我这个默认不成立 —— 备用模型会跳过工具、直接凭记忆编一个日活数字。

2.3 ★ 三个关键设计决策（都有真实教训）
--------------------------------------------------------------------------------
【决策 1】先导入数据，后建索引 —— 不要反过来
    教训：最初先建索引再导数据，导入速度慢了 3~5 倍。
    原因：每插入一行都要维护 B+ 树索引，百万行规模下开销被放大。
    正确做法：批量导入 → 再 CREATE INDEX。
    延伸思考：这也是数据仓库 ETL 里「批量装载前先禁用索引/约束」的同一原理。

【决策 2】真实 Steam 数据存在 16.9 万组重复主键，必须去重
    教训：原始 CSV 里 (user_id, appid) 有大量重复组合，直接入库会让
    「用户-游戏」关联分析出现重复计数，指标全部失真。
    做法：清洗阶段按业务语义聚合去重（同一用户同一游戏的多条时长记录合并）。
    延伸思考：这是「数据质量直接影响指标可信度」的最好例证——如果不做
    这一步，后面再怎么优化 SQL 都没意义。

【决策 3】留存率用幂律公式，而不是线性衰减
    原因：真实游戏的留存曲线是「前期陡降、后期趋平」（D1 掉一半，D30 还在
    10% 附近），线性衰减不符合经验规律，会让模拟数据假得不真实。
    延伸思考：模拟数据的价值在于「业务规律要对」，而不是「数字好看」。

三、Phase 2 · 指标语义层与 SQL 生成核心
================================================================================

3.1 ★ 核心设计思想（全项目最重要的一句话）
--------------------------------------------------------------------------------
    用户问题  →  LLM 只做「映射到 metric_id + 抽取参数」
              →  程序按注册表里的预审 SQL 模板填参生成 SQL
              →  安全校验  →  执行

    这样做换来三件事：
      · 准确率：分类+抽参比"生成 SQL"简单得多，模型出错概率大幅下降
      · 可治理：口径写在 JSON 里，改口径不改代码（配置驱动）
      · 安全性：SQL 模板是白名单资产，天然免疫大部分注入

3.2 交付物
--------------------------------------------------------------------------------
    src/metrics/metrics_registry.json   12 个指标定义（单一事实来源）
    src/metrics/registry.py             注册表加载器 + 语义检索
    src/sqlgen/generator.py             SQL 生成器（模板填参 + 日期表达式）
    src/sqlgen/validator.py             SQL 安全校验器
    src/sqlgen/executor.py              SQL 执行器（只读 + 超时 + 行数上限）
    src/exceptions.py                   5 类业务异常
    src/config.py                       新增 SQL_MAX_ROWS / SQL_TIMEOUT_SECONDS
    tests/                              216 个用例

3.3 为什么用 JSON 而不是 Python dict
--------------------------------------------------------------------------------
    · JSON 是纯数据，产品/运营/数据分析师能直接维护和评审，不需要会 Python
    · 未来要迁移成数据库表或后台管理页面时，成本最低
    · 逻辑（registry.py）与数据（JSON）分离，是配置驱动设计的标准做法

3.4 ★ 四层安全防线（常被追问「你怎么保证 SQL 安全」）
--------------------------------------------------------------------------------
    第一层  模板受控    LLM 碰不到 SQL 文本，只能传 metric_id 和参数
    第二层  语法校验    只允许 SELECT / WITH；表白名单比对；强制补 LIMIT
    第三层  只读连接    用 file:...?mode=ro 打开 SQLite，物理上无法写
    第四层  参数绑定    参数走 ? 占位符，不做字符串拼接

★ 关键点：这四层是「纵深防御」，任何一层被绕过都还有下一层。如果只说
  "用正则过滤了 DELETE"，会被认为安全思维不足；说清四层递进关系才到位。

★ Phase 6 补的第五层（答案来源校验，见 7.4）：这四层**全部位于 SQL 出口**，
  隐含前提是"模型一定会去查库"。真机验证时备用模型跳过了全部工具调用、
  直接凭记忆编出一个日活数字 —— 四层防线对它完全无感。
  所以第五层补在**模型输出答案的出口**：本轮没有一次成功取数、答案里却出现
  数据型数字，就判定为疑似编造，强制重查，补救用尽则拦截整条回答。
  ★ 设计要点：安全的层次要跟着**数据流**走，而不是跟着"最危险的组件"走。

3.5 ★ 两个精妙设计
--------------------------------------------------------------------------------
【设计 A】生成两份 SQL：执行版 + 展示版
    执行版 = 填好参数的最终 SQL（给数据库跑）
    展示版 = 保留 :param 占位符 + 附参数表的 SQL（给人看，体现"我没乱写 SQL"）
    原因：产品需求既要"可执行"又要"可解释"。只给执行版，用户看到一堆硬编码
    日期会怀疑；只给展示版，又没法直接跑。两份各司其职。

【设计 B】用 progress handler 实现真正的 SQL 超时中断
    做法：sqlite3 的 set_progress_handler 每执行 N 条 VM 指令回调一次，
    在回调里检查是否超过 SQL_TIMEOUT_SECONDS，超时返回非 0 直接中断查询。
    原因：SQLite 没有内置 statement_timeout（不像 PostgreSQL 有
    statement_timeout 参数）。如果只在执行前/后判断时间，慢查询会一直卡住。

3.6 日期相对表达式（解决"默认参数会过期"的问题）
--------------------------------------------------------------------------------
    模板里写 :start_date，参数的 default 可以写：
        "@data_end"            数据截止日
        "@data_end-6"          截止日前推 6 天（默认看最近 7 天）
        "@data_end-:day_n"     引用前面 int 参数的值（用于留存批次窗口）
    原因：如果默认值写死 '2026-09-17'，过几天数据更新了默认口径就错了。
    相对表达式让「默认最近 7 天」永久成立。

3.7 修复的两个缺陷（真实 bug，值得记）
--------------------------------------------------------------------------------
【缺陷 1】D7/D30 默认参数返回 NULL
    现象：查 D7 留存返回空。
    根因：cohort_start 的默认值 "@data_end-6" 是固定 6 天前，但没有随 N 前移；
    且窗口长度应该是恒定的 7 天，否则不同 N 的口径不可比。
    修复：cohort_start = "@data_end-6-:day_n"，cohort_end = "@data_end-:day_n"。
    本质：日期表达式要支持引用整数参数，且「整体前移 N 天、窗口长度恒为 7 天」
    才能保证 D1/D7/D30 口径一致。

【缺陷 2】FROM 子句正则匹配跨查询块
    现象：带 CTE 的 SQL（WITH a AS (...), b AS (...) SELECT ...）提取表名时
    把子查询块误判成表名。
    根因：正则 [FROM|JOIN]\s+(\w+) 会一直匹配到下一个 SELECT/WITH 才停。
    修复：终止符里加入 SELECT / WITH，遇到新查询块边界立即停止。
    本质：正则解析 SQL 永远是"够用就好"，真要严谨得用 sqlparse 之类的 AST 解析。

4.2 ★ 为什么手搓 ReAct，而不用 LangChain
--------------------------------------------------------------------------------
这是很可能会被追问的问题，答好能显著加分。

理由一：项目本身就是「AI 应用能力」的展示，用现成框架等于把这块能力藏起来了。
理由二：ReAct 循环的本质只有几十行——想 → 做 → 看 → 重复。
        用 LangChain 反而要学它的抽象（AgentExecutor / Tool 基类 / 回调体系），
        调试时还得穿透框架源码，成本更高。
理由三：可控性。熔断阈值、异常兜底、Token 统计这些都需要精确控制，
        框架的默认行为经常和需求不一致。
理由四：零依赖。核心 Agent 逻辑不依赖任何第三方框架，只依赖 openai SDK。

客观表述方式（避免显得"为了造轮子而造轮子"）：
    「如果是在生产环境快速交付，我会选 LangGraph，它的状态机和持久化能力更省事；
      但这个项目的核心目标之一就是展示我对 Agent 循环机制的理解，
      所以手搓更合适。」

4.3 三个工具的设计（Function Calling）
--------------------------------------------------------------------------------
    工具 1  list_metrics()
            返回指标目录（ID / 名称 / 分类 / 别名 / 参数名）
            用途：模型不确定有哪些指标可用时先看一眼

    工具 2  get_metric_detail(metric_id)
            返回单个指标的完整口径：业务定义、参数表、维度、单位、
            输出字段、易错点备注
            用途：★ 这是"口径知识放在注册表里、让模型运行时去查"的关键

    工具 3  query_metric(metric_id, params)
            真正执行：生成 SQL → 校验 → 查询 → 返回结果
            用途：取数

★ 为什么是 3 个而不是 1 个「万能工具」？因为工具描述就是模型的"能力边界说明"。
  拆开的好处是模型能分步思考：先确认指标存在 → 再确认参数怎么填 → 最后才查数。
  这三步对应三种不同的失败模式，拆开后每一步的错误都能被精确定位和纠正。

4.4 ★ 三个关键设计决策
--------------------------------------------------------------------------------
【决策 1】错误分类重试：401 不重试，429/5xx 才重试
    做法：_is_retryable() 读异常里的 status_code 区分。
    原因：无脑重试 401 会白等 3 轮指数退避（好几秒），最后还是降级到备用
    供应商——纯属浪费时间。4xx 里"请求本身有问题"类错误应该立刻切换，
    只有网络抖动、限流、服务端错误才值得等。
    延伸思考：这体现了"错误可分类"的工程思维，而不是 try/except 一把梭。

【决策 2】工具结果双份输出：content（文本）+ data（结构化）
    content = Markdown 文本，喂给 LLM 读
    data    = 结构化 dict（columns + rows），留给前端画图（Phase 4 用）
    原因：★ 同一次查询产生两种表示，从机制上杜绝"图表上的数字和 Agent
    说的话对不上"。如果让前端自己去数据库再查一遍，两份数字就可能不一致。

【决策 3】工具失败 = 观察结果，而不是抛异常
    做法：工具内部捕获异常，把错误信息包装成一句人类可读的提示返回给模型。
    例：模型把参数名写成 days，工具返回
        「参数名不认识。可用参数：start_date, end_date」
    原因：★ 模型看到这句话，下一轮就能自己改对。反馈质量直接决定自我纠错
    能不能成功。如果直接抛异常中断循环，模型永远没机会修正。
    这也意味着：写工具的错误提示语时，要站在"模型能不能看懂并据此修正"的
    角度去写，而不是写给人看的堆栈信息。

4.5 Token 预算控制
--------------------------------------------------------------------------------
    config 里 LLM_TOOL_MAX_ROWS = 60
    含义：数据库层允许一次返回 500 行（供前端展示表格），但塞进 LLM 上下文的
    文本被截断到 60 行。
    原因：全塞进去既贵（token 成本）又挤占推理空间。结构化 data 保留全量，
    所以前端的完整数据不受影响。

4.6 系统提示词的 6 条硬性规则
--------------------------------------------------------------------------------
    ① 只能用指标目录里的 metric_id，不许自己编造
    ② 不确定口径时先调 get_metric_detail 查，不要凭常识猜
    ③ 禁止编造数字，所有数字必须来自 query_metric 的返回
    ④ 数据窗口之外的提问要诚实说明"超出覆盖范围"，并给出替代方案
    ⑤ 样本量过小时必须提醒（比如批次样本只有几百人）
    ⑥ 涉及因果推断（如"是不是版本导致的"）必须说明"相关不等于因果"，
      重大决策类建议必须提示「需人工复核后执行」

5.2 ★ 四个关键设计决策（设计要点）
--------------------------------------------------------------------------------
【决策 1】Agent 实例用 st.cache_resource，问答结果用 st.session_state
    Streamlit 的执行模型很特殊：**每次交互都会把整个脚本从头重跑一遍**。
    不缓存会付出两份代价：
      · 每点一次按钮就重建一次 LLM 客户端（连接池、重试状态全丢）；
      · 用户展开侧边栏、切换图表纵轴都会触发重跑 → 重新调一次 API。
      一次 5 轮的对话能悄悄烧掉几十次调用，而账单上完全看不出来为什么。
    分工口诀：带句柄/连接的**单例资源**用 cache_resource，
              只读的**纯数据**用 cache_data（会序列化副本，外部改不脏缓存）。

【决策 2】AgentStep 必须把结构化数据带出来
    工具返回本来就有两份输出：content（给模型看的文本）和 data（给程序用的结构化数据）。
    但 Phase 3 的 AgentStep 只存了 content，把 data 丢了 —— 到画图时才发现没数据。
    修法**不是**让前端去反解析 Markdown 表格（列名带空格、NULL 写法一变就崩），
    而是在 AgentStep 上加一个 result 字段原样带出来，并补一条测试断言它不丢。
    一句话：文本给人，结构化数据给程序，两条路各走各的。

【决策 3】「选图策略」和「画图」拆成两个函数
    pick_chart_spec() 是纯逻辑（输入 dict → 输出 ChartSpec），不碰 streamlit / plotly；
    build_figure() 才真正调 Plotly。
    为什么值得拆？因为选错图是**产品事故**（留存趋势画成柱状图，拐点就没了），
    必须有测试兜住；而写在 Streamlit 脚本里的逻辑是测不了的
    （一 import 就连带整个运行时，没法在 pytest 里跑）。

【决策 4】人工确认节点不是"弹个提示"，而是一个有留存的动作
    硬约束第 4 条要求「重大决策类分析必须留人工确认节点」。
    前端落地成：复核人输入框 + 勾选确认项 + 写入审计日志（谁、何时、确认了哪条结论）。
    为什么做得这么重？因为「人工兜底」若只停留在提示文案上就是一句空话 ——
    上线后出了问题，必须能回答「当时是谁拍的板」。

5.3 自动选图规则（本阶段的产品内核）
--------------------------------------------------------------------------------
    数据形状                        出的图      理由
    --------------------------------------------------------------------------
    没有数据行                      不出图      画空图不如直说"没查到"
    新手引导漏斗（多层步骤列）      漏斗图      分层递进过程，漏斗能看出哪层流失最多
    含日期列 + 数值列               折线图      时间序列看趋势，折线是默认正确解
    含分组维度 + 数值列 + 多行      柱状图      组间对比用柱，长短一眼可比
    只有一行数据                    指标卡      一个点的折线图毫无信息量

    两个最容易写错的细节（都写了测试）：
    · 默认纵轴必须挑 _pct 列，不能挑「第一个数值列」。
      否则按模板列序会挑到 cohort_size，运营打开页面看到的是一根根
      「样本量柱状图」，完全答非所问；其他数值列保留为下拉可切换项。
    · 漏斗指标要特判，且必须排在「单行 → 指标卡」规则之前。
      否则 8 列的信息会被压成一个注册人数，最有价值的逐层流失全部丢失。

5.4 ★ 测试逼出来的两个真实缺陷
--------------------------------------------------------------------------------
【缺陷 1】单位被套到了所有数值列上
    现象：留存率卡片是 42.61%，但「样本量」显示成 812%、「留存人数」显示成 346%。
    根因：指标单位被无差别地应用到了同一行的每个数值列上。
    修复：单位只属于主指标列，其余列不带单位。
    本质：**单位是"列"的属性，不是"结果"的属性** —— 单位错了，数字就不可信了。

【缺陷 2】漏斗图渲染不出来
    现象：pick_chart_spec 判定为 funnel，但 build_figure 返回 None，界面一片空白。
    根因：渲染入口有一道统一守卫 `if not spec.y: return None`，
          而漏斗图的 y 本来就是空的（数值来自 funnel_steps，不是某一列）。
    修复：守卫只对 line / bar 生效。
    本质：**通用守卫条件遇到特例分支时会变成杀手**。
          写守卫时必须自问：这个前置条件对**所有**分支都成立吗？

6.1 这一阶段要回答的问题
--------------------------------------------------------------------------------
前四个 Phase 证明了「这个系统能跑通」，但跑通 ≠ 可信。一定会被问：
「你怎么知道它答得对？」如果只能回答「我试了几次都对」，项目就停在 Demo 层面。

所以评测体系要把「答得对」拆成三个**可量化**的问题：

    ① 模型有没有选对指标？          → 指标映射准确率
    ② 模型有没有把参数抽对？        → 参数抽取准确率
    ③ 模型说的数字能不能对上数据？  → 答案数字可追溯率

③ 最关键 —— 它是「零编造」这个核心主张的**机器化证明**。
靠人眼看「它好像没瞎说」是不可复现的，必须用程序逐字对账。

6.2 交付物
--------------------------------------------------------------------------------
    src/eval/metrics.py         评测核心算法（纯函数：数字抽取 / 四档分类 / 汇总）
    src/eval/eval_set.py        评测集加载器（复用 SQLGenerator 解析期望参数）
    src/eval/eval_set.json      18 条标准问答用例（覆盖全部 12 个指标 + 2 条边界）
    src/eval/runner.py          双路径执行器 + 纯文本报告生成
    src/eval/__init__.py        包出口
    scripts/run_eval.py         命令行入口（实时进度 + 报告落盘 + JSON 落盘）
    tests/test_eval_metrics.py  55 个用例

    运行方式：
        python scripts/run_eval.py                    # 全量 18 条（会真实调模型）
        python scripts/run_eval.py --limit 3          # 开发期先跑 3 条验证流程
        python scripts/run_eval.py --cases E01,E17    # 只跑指定用例
        python scripts/run_eval.py --dump docs/04_评测原始数据/评测结果_Phase5.json   # 附带模型原话

    测试总量：369 个用例全绿（Phase 4 的 314 + Phase 5 的 55）

6.3 ★ 核心设计一：双路径对账（这是整个评测体系的地基）
--------------------------------------------------------------------------------
    对每一条用例，跑两条**互不相干**的路径：

        路径 A（被测对象）：把问题交给 Agent，看它怎么理解、查了什么、答了什么
        路径 B（真值）：用用例声明的期望 metric_id + params，**直接调工具**查一次

        然后把 A 的答案拿去和 B 对账。

    ★ 为什么不能拿 A 自己查出来的数据当标准？
      因为如果 Agent 把「最近 14 天」错理解成「最近 7 天」，它查出来的数字
      在它自己那套逻辑里是**完全自洽**的 —— 拿它自己的数据对账，永远满分。
      这就是「自己印证自己」的陷阱。所以真值必须有一条**完全不经过 LLM** 的路径。

    这条设计在真机上立刻见效：E15 问「v2.0.0 上线后留存变好了吗」，
    模型额外查了 D7 口径，报出「样本 376 人」。376 不在 D1 的真值切片里，
    被如实标成「存疑」—— 如果放行模型自己查的数据，这个「查错口径」的信号
    就永远抓不出来了。

6.4 ★ 核心设计二：数字分四档，机器做初筛、人工做终审
--------------------------------------------------------------------------------
    「答案里的数字对不上参考值」有好几种可能，程序没法直接区分：
        · 编造（严重问题）
        · 口语化近似（把 533 说成「530 左右」）
        · 合理衍生（自己算了 7 天均值 517、算了个涨幅 15%）
    所以不做「对不上就定性为编造」，而是分成四档，只把最后一档交给人：

        严格匹配 → 精确命中参考值（容差 0.5%，只允许四舍五入）
        合理近似 → 落在宽松容差内（3%），属于正常口语表达
        可推导   → 能由参考值算出来（合计 / 均值 / 极差 / 两两差值 / 比值 / 涨跌幅）
        存疑     → 以上都不是  ← **只有这一类需要人看**

    判定顺序必须是「先硬后软」：严格 → 近似 → 推导。
    如果反过来先判推导，一个恰好等于某对参考值之差的编造数字就会被归进
    「可推导」，把真问题藏起来 —— 这比误报更危险。

    ★ 这条分层是**被真实数据逼出来的，不是一开始就设计好的**（详见 6.6 缺陷 1）。
      指标一旦开始误报，就没人再信它了 —— 这比没有指标更糟。

6.5 评测集设计（eval_set.json）
--------------------------------------------------------------------------------
    用例结构（关键：**只声明期望指标 + 期望参数，不写期望数值**）：
        case_id / question / category / notes
        expected_metric_id      期望模型映射到的指标
        expected_params         期望抽取到的参数（空 dict 表示"不校验参数"）
        reference_metric_id     真值用哪个指标算（默认同 expected）
        reference_params        真值用什么参数算（默认继承 expected_params）
        expect_no_query         超范围用例：期望它不查数

    ★ 为什么不写期望数值？因为数值会随数据更新而失效。评测集里写死
      「42.66%」，下次数据一变整份评测集就废了。**尺子必须自适应**：
      期望值在运行时由路径 B 现算，评测集只负责声明"该问什么、该查什么"。

    ★ 参数解析复用 Phase 2 的 SQLGenerator，而不是自己再写一套。
      否则会出现「系统按规则 A 解析 @data_end-13、评测按规则 B 校验」的错位，
      评测结果就不可信了。

    分类覆盖：活跃 3 / 留存 4 / 增长 2 / 商业化 4 / 渠道 1 / 版本 2 / 边界 2
    其中两条边界用例专门考「知不知道自己的边界」：
        E17 去年 12 月的日活是多少？   → 超出数据窗口，应拒答
        E18 帮我预测一下下个月的新增用户数。→ 系统只做描述不做预测，应拒答

6.6 ★ 真机评测暴露的四个缺陷（这是本阶段最有价值的部分）
--------------------------------------------------------------------------------
第一轮全量评测结果：映射 100% / 参数 88.89% / 数字可追溯率 95.00%。
数字上看还不错，但把「存疑数字」逐条拉出来人工复核后，发现**四个缺陷**：

【缺陷 1】评测规则本身在误报（最严重）
    现象：E01「最近 7 天的日活怎么样？」这种最简单的用例，14 个数字里
          3 个被判「对不上」，可追溯率只有 78.6%。
    人工核查：那 3 个分别是「7 天均值 517」「回升约 15%」「稳定在 530 左右」
              （真实值 533）—— 全都是**正确**的分析表达，一个都没编。
    根因：第一版只有「对上/对不上」两档，用 0.5% 的严格容差去卡口语表达，
          而且推导池只认「原样命中」，不认模型自己算的衍生值。
    修复：重构成四档分类 + 新增 3% 宽松容差 + 新增 derived_values() 推导池。
    本质：**一个会误报的指标，比没有指标更糟**。它会让人以为模型有 21% 在编造，
          实际上一个数都没编。而且误报多了，复核的人就不再认真看这个指标了。

【缺陷 2】真值参数没有继承期望参数（隐蔽但致命）
    现象：单测 `test_eval_set_resolves_relative_date_expressions` 直接失败。
    根因：未声明 reference_params 的用例拿到空 dict，于是真值查询用的是
          **系统默认参数**。E07「最近两周」期望 14 天窗口，真值却按默认 7 天算 ——
          模型答对了，反而被判「数字对不上」。
    修复：未声明时继承 expected_params。
    本质：**尺子量错了，还怪被测对象**。这是评测里最隐蔽的一类错误，
          因为它表现为"模型不行"，而不是"评测器坏了"。

【缺陷 3】参数判定只看最后一次调用，惩罚了更充分的分析
    现象：E15 参数判为未通过（期望 day_n=1，实际 day_n=7）。
    人工核查：模型在同一轮里**并发查了 D1 和 D7 做对比**（这恰恰是加分的），
              最后一次是 D7，于是被判错。它明明查对了 D1。
    修复：判定口径改成「任意一次调用命中即通过」，和指标映射保持一致。
    本质：**评测要惩罚的是漏查，不是多查。** 与缺陷 1 是同一类病：
          指标设计不当，会把正确行为判成错误行为。

【缺陷 4】数字抽取规则漏掉三类"非数据值"
    现象：E07 的存疑数字是「-05」，E13 是「3、09」。
    根因三条：
        · 模型用 Markdown 表格列日期时写成「09-05」（省略年份），
          数字正则把它拆成 09 和 -05；
        · 「卡在第 3 步」里数字前面是空格，而旧规则只看**紧邻的前一个字符**，
          于是「第」没拦住这个 3；
        · 「3 个月」的「个」不在时间量词表里。
    修复：补简写日期正则（且必须排在 4 位年份规则**之后**）、
          前缀判断改成 rstrip 后 endswith、量词表补「步 / 个」。

    修复后重跑：映射 100% / 参数 100% / 数字可追溯率 96.99%（161/166）。
    剩下 5 个存疑数字全部人工确认过，都属于合理情况：
        E12「3」    —— 行业经验值「LTV/CAC > 3 才算买量健康」
        E13「3」    —— 「步骤 3」的序号残留
        E15「376」  —— 用错口径（D7）查出的样本量，**真信号**
        E16「18.51、2」—— 模型额外查了其他时间窗口做对比

6.7 ★ 最终评测结果（2026-09-18 真机，18 条用例全跑）
--------------------------------------------------------------------------------
    ┌────────────────────────────┬───────────┬──────────────────────────┐
    │ 指标                       │ 结果      │ 说明                     │
    ├────────────────────────────┼───────────┼──────────────────────────┤
    │ ① 指标映射准确率           │ 100.00%   │ 16 / 16（2 条边界不适用）│
    │ ② 参数抽取准确率           │ 100.00%   │ 9 / 9                    │
    │ ③ 答案数字可追溯率         │  96.99%   │ 161 / 166 个数字         │
    │ ④ 超范围拒答正确率         │ 100.00%   │ 2 / 2                    │
    ├────────────────────────────┼───────────┼──────────────────────────┤
    │ Agent 正常返回             │ 18 / 18   │ 无一条因异常中断         │
    │ 平均迭代轮数               │ 2.67 轮   │ 收敛很快                 │
    │ 平均 token 消耗            │ 7,160.8   │ 总计 128,895             │
    │ 平均响应耗时               │ 3,244 ms  │                          │
    └────────────────────────────┴───────────┴──────────────────────────┘

    ★ 设计要点：这组数字里最有含金量的是「③ 96.99%」—— 它意味着模型在
      166 个数字里只有 5 个需要人工看一眼，且经核查全部不是编造。
      这是"零编造"从一句自我感觉，变成了一个可复现、可对比的数字。

    ★ 成本数据同样是产品视角的加分项：平均 7.2k token / 3.2 秒 / 2.67 轮。
      能报出这组数，才谈得上「优化」—— Phase 6 正是拿这组基线做的 prompt
      精简与缓存优化，前后对比见 7.3 与 7.7。

--------------------------------------------------------------------------------
    每次跑完会落两份文件：
        docs/评测报告_Phase5.txt     纯文本报告（总览 + 逐例明细 + 需人工关注）
                                     ↑ Phase 5 当时的路径写法；该文件在 Phase 6 已被覆盖更名
        docs/04_评测原始数据/评测结果_Phase5.json   结构化结果（含模型原话，供离线复查）

    ★ Phase 6 起报告文件更名为 docs/03_评测报告/评测报告_Phase6.txt（报告路径不再是"某个
      Phase 专属"，而是"最新一次跑的结果"），评测结果按版本号落盘
      （docs/04_评测原始数据/评测结果_Phase6_v11.json = 评测集 v1.1 的结果）。
      Phase 5 那一版的报告原文只留在本文档附录 B 里，作为历史基线。

    ★ 为什么报告是纯文本而不是 JSON？因为它是给人看的（自己复盘、演示展示），
      可以直接贴进本文档，不依赖任何工具。需要机器复算时，to_dict() 已经
      提供了结构化出口，两者不冲突。
    ★ 为什么要把模型原话也存下来？因为报告里只会写「存疑数字：25」，
      而人复核时必须看到**原话上下文**才能判断它是编造还是正常表达。
      存下来才能事后离线复查，不用重跑（重跑一次要烧 13 万 token）。

    评测算法自己也有边界，报告末尾写明了：
        程序只能判断「数字有没有对上参考数据」，
        无法判断「结论是否合理」「因果推断是否成立」—— 后者仍需人工复核。

7.1 这一阶段要解决什么
--------------------------------------------------------------------------------
前五个 Phase 解决了「能不能跑通」「答得准不准」。Phase 6 要解决的是另一类问题：
**一个能拿得出手的作品，还差什么**。具体拆成四件事：

    ① 门面 —— 读者打开仓库的前三分钟，能不能看懂这个项目在做什么、凭什么可信
    ② 成本 —— 每次请求都带的系统提示词是固定开销，它到底占多少、能不能降
    ③ 容错 —— 主备降级写了代码，但没在真机上验证过，它究竟会不会切
    ④ 覆盖 —— 18 条评测用例只覆盖主干问法，运营的口语化问法扛不扛得住

★ 这四件事的共同点是：**它们都不影响"能不能跑"，但决定"敢不敢拿去讲"。**
  这也是我把它们放在最后一个 Phase 的原因 —— 先把功能做扎实，再谈打磨。

7.3 成本优化：prompt 精简 + 缓存计量（一条完整的闭环）
--------------------------------------------------------------------------------
【问题定义】
    第八节 8.4 已经量化过一笔账：第 4 组问题一次工具都没调，仍消耗 2,316
    tokens —— 因为 12 条指标目录是**每次请求都要带的固定开销**。
    小问题上，固定开销占比能超过 40%。这就是要优化的地方。

【动作一 · 精简指标目录】
    · 目录拆成两个形态，按场景取用：
        summary_line()   完整版（ID / 名称 / 分类 / 别名 / 参数名），
                         留给 list_metrics 工具按需查 —— 反正只查一次
        catalog_line()   紧凑版（去掉分类列），塞进系统提示词 —— 每次请求都带
      ★ 为什么要拆两个形态：同一个信息，**"每次请求都带"和"按需查一次"的
        成本差一个数量级**。固定开销要按"每条请求都付"来设计，不能图省事共用一份。
    · 别名去重（新增 _PARENTHETICAL / _ALIAS_NOISE / _ABBR_SPLIT 三个正则）：
      剔除与指标名主干重复、与名称括号内缩写重复、与 metric_id 重复的噪音别名。
      例：指标名「留存率（D1/D7/D30）」里的括号内容本身不是别名，不该重复出现在
      别名列里；别名上限 6 个，超出截断。
    · 删掉「【可用指标目录】」这个重复表头（to_catalog_text() 自带表头，
      提示词里又写了一遍）。

【量化收益】
    指标目录      1,447 → 1,242 字符（-14.2%）
    系统提示词    2,936 → 2,722 字符（-7.3%）
    全量评测平均  7,160.8 → 6,796.4 tokens（-5.1%，同一组 18 条用例）

【动作二 · 缓存计量：把"省钱"变成可观测指标】
    ★ 为什么只精简还不够：系统提示词在多次请求之间高度重复，主流供应商都有
      prompt caching，命中后这部分按约 1/10 计价。所以真正该盯的指标不是
      「提示词有多长」，而是「缓存命中率有多高」—— 长度是手段，命中率才是结果。
    · LLMResponse 新增 cached_tokens 字段，兼容两种响应结构：
        DeepSeek    扁平字段  usage.prompt_cache_hit_tokens
        OpenAI/GLM  嵌套字段  usage.prompt_tokens_details.cached_tokens
      ★ 这是"多供应商抽象"要付的必然代价：同一件事各家字段名不一样，
        适配层要吸收掉，不能让它渗透到业务代码里。
    · 评测汇总新增 cache_hit_rate。★ 分母取「输入 token」而不是「总 token」——
      总 token 里混着输出，用总 token 当分母会把命中率算低，口径不干净。
    · 实测：缓存命中 190,332 / 输入 209,878 = 90.69%（平均每条命中 6,140 tokens）

【设计要点】这是「Agent 产品的成本结构」这类问题的完整答法：
    先量化基线（7.2k token/条）→ 把账单拆成固定开销与可变开销 →
    对固定开销做精简（-5.1%）→ 再叠缓存（命中率 90.69%，计费层面再降一档）→
    最后用同一把尺子复测。注意 -5.1% 是"精简"单独的功劳，
    缓存收益体现在**计费**而不是 token 数上，两者不能混着说。

7.4 ★ 主备降级真机验证 + 第五层防线（本阶段最有价值的发现）
--------------------------------------------------------------------------------
【验证一 · 降级链路（5 点全通过）】
    方法：把 .env 里的 DEEPSEEK_API_KEY 临时清空，观察是否自动切到 GLM。
        ① 客户端主备顺序为 ['deepseek', 'glm']                        ✓
        ② 主 Key 缺失时只尝试备用，**没有浪费一次 DeepSeek 调用**      ✓
        ③ 备用端到端答出结果（provider=glm，model=glm-4-flash）        ✓
        ④ 备用也失败时错误信息完整（带「已按顺序尝试 智谱 GLM」+ 原始错误码）✓
        ⑤ 两个 Key 都没有 → LLMNotConfiguredError，文案准确            ✓
    ★ 第 ② 点是关键：如果实现成"先试主、失败了再切"，清空 Key 会先撞一次 401。
      实际实现是**先检查 Key 是否存在再决定尝试谁**，所以不会白烧一次调用。

【验证二 · 真机爆出的严重缺陷（★ 这段是本阶段最该讲的）】
    现象：GLM-4-Flash 面对「最近 7 天的日活是多少」，**跳过全部工具调用，
          直接编出「日活是 100,000 人」**，同一问题两次稳定复现。
          而留存、版本、渠道类问题它都正常调用了工具 —— 越是"简单到不用查"的
          问题，越容易被它凭记忆糊弄过去。
    为什么危险：四层防线**全在 SQL 出口**。可模型压根没走到 SQL 那一步。
          四层防线对它完全无感 —— 它编的数字比任何错误 SQL 都更接近用户。
    根因：「禁止编造」当时只是提示词里的一句软约束。备用模型的指令遵循能力
          弱于主模型，**软约束被击穿**。这印证了一条经验：
          提示词是"请求模型配合"，架构才是"保证系统正确"。

    → 新增第五层防线：答案来源校验（src/agent/react_agent.py）
      触发条件（两条必须同时成立）：
        ① 本轮没有任何一次成功的 query_metric（判据是工具返回的 result.ok，
           不是"调过就算"——调用失败也算没取到数）
        ② 回答里出现了「数据型数字」
      ★ 为什么必须两条同时成立，单看任一条都不行：
        · 只看「没取数」就拦 → 正常的超范围拒答、寒暄会被误伤；
        · 只看「有数字」就拦 → 拒答文案里天然带日期（2026-06-20）。
      命中后：追加提醒 → 强制重新取数 → 补救上限 AGENT_GUARD_RETRIES = 1
      补救用尽仍在编造：返回 ok=False + 固定文案（_GUARD_BLOCKED_ANSWER），
      ★ **不把编造的数字给用户看**，error 写明「回答中出现无法溯源的数值
        （疑似编造），已被来源校验拦截」。
      拦截过程记为一个 AgentStep(kind="guard") 进 trace，前端「执行过程」里
      能看到「模型编了 → 系统拦了 → 模型重查了」的完整链路，而不是悄悄重试。

    ★ 关键实现细节（追问一定会问到这里）：
      · 三个模块级正则 _DATE_LIKE / _VERSION_LIKE / _DATA_NUMBER，
        判定顺序必须是「先剔日期 → 再剔版本号 → 最后看数据值形态」。
        顺序反了，含「2026-06-20」「90 天」的正确拒答就会被误判成编造。
      · _DATA_NUMBER 只认三类数据值形态：百分比、千分位、3 位以上连续数字。
        ★ 为什么是"3 位以上"：把「7 天」「2 个渠道」这类小数字排除在外，
          它们本身不构成"数据结论"，抓它们只会制造误报。
      · _VERSION_LIKE 必须写成 [vV]\d+(\.\d+)+|\d+(\.\d+){2,}（要求带 v 前缀
        或至少两个点）。我第一版写成 [vV]?\d+(\.\d+)+，结果把 45.00 这种**小数**
        也当版本号剔掉了 —— 而小数恰恰是这条防线最该抓的形态
        （留存率 42.66%、付费率 3.85% 全是小数）。防线等于形同虚设。
        教训记在第九节第 19 条。
      · 提醒用 user 角色追加，而不是 system：多数供应商对「对话中段的 system
        消息」支持不一致，用 user 兼容性最好，语义上也说得通 —— 相当于
        「用户（其实是系统）对它刚才的回答提出了质疑」。

    ★ 复验结果（同一个问题，防线生效前后）：
        修复前：1 轮 / 0 次工具调用 / 编造「日活是 100,000 人」
        修复后：4 轮 / get_metric_detail → query_metric /
                答出真实逐日数据 465 / 497 / 544 / 509 / 534 / 537 / 533

    ★ 设计要点：这件事说明「安全防线要沿**数据流**布置，而不是只堆在最危险的那一层」。
      我原来的四层防线都建在 SQL 出口，隐含假设是「模型一定会去查」。
      真机告诉我这个假设不成立。所以防御要补在**模型输出答案的那个出口**——
      这也是整条链路上唯一还没设防的环节。

【验证三 · 备用链路复验（同日二轮，清空 DEEPSEEK_API_KEY 全走 GLM）】
    目的：换过 GLM 的 Key 之后，把整条备用链路重跑一遍，确认防线不是"只对
          当时那一问有效"。结论：**防线稳定生效，且顺带验证了两件事**。

    ① 编造行为是**系统性**的，不是偶发 —— 同一个问题连问两次，
       两次都在第 1 轮直接编「日活是 100,000 人」，两次都被来源校验拦下，
       两次都强制重查后答出真实数据：
         第 1 次：1 轮编造 → 拦截 → get_metric_detail → query_metric →
                 465/497/544/509/534/537/533（4 轮，18.5 秒，9,382 tokens）
         第 2 次：1 轮编造 → 拦截 → 同样的取数路径 →
                 465/497/544/509/534/537/533（4 轮，12.1 秒，9,257 tokens）
       ★ 两次拦到的文案一字不差（「最近 7 天的日活是 100,000 人。」）——
         说明这确实是该模型在这类问题上的**固定行为模式**，而不是随机幻觉。
         ★ 也就是说：第五层防线不是"以防万一"，而是**必需的**。

    ② 顺带验证了「工具失败返回观察结果」的设计在备用模型上同样有效：
       问「次留是多少」时，GLM 第一轮传了 `day_n=2`（无效参数，注册表只支持
       1/7/30），工具返回 ok=False 并给出可用参数提示；GLM 第二轮先调
       get_metric_detail 看口径，第三轮改传 `day_n=1` 成功取数，答出 41.95%。
       ★ 这印证了 3.2 的设计选择：**工具失败不抛异常、而是返回"可观察的失败"**，
         模型才有机会自我纠错。如果这里抛异常，整轮对话就直接中断了。

    ③ 人工确认约束在备用模型上也生效：版本类问题（「v2.0.0 上线后留存变好了吗」）
       GLM 的结论里主动带上了「样本量偏小，结论仅供参考」+「以上建议需人工复核
       后执行，建议结合买量成本、竞品动态等因素共同判断」。
       且它报出的 46.36%（版本后 D1）/ 40.30%（版本前 D1）与 Phase 2 的
       基线结论「版本后 D1 留存比版本前高 6.1 个百分点」一致（实测差 6.06）。

    ④ ★ 复验暴露的新盲区：**缓存命中率在备用链路上是看不到的**。
       GLM 的 usage 里没有缓存字段，实测 cached_tokens 恒为 0 ——
       意味着 7.3 那个 90.69% 的命中率**只反映主供应商（DeepSeek）**，
       备用链路的缓存收益目前是黑盒。
       ★ 这不影响正确性，但影响"成本可观测性"的完整性 —— 属于已知局限，
         已记入 7.8 的遗留项。

    ⑤ ★ 复验暴露的第二个新事实：**备用链路的延迟显著更高**。
       GLM 这 4 问耗时 12.1 / 14.9 / 15.1 / 18.5 秒，
       vs 主链路 31 条评测平均 3,372 ms —— **慢 4~5 倍**。
       ★ 产品结论：降级保的是"可用性"，不是"体验"。前端应该在切换备用时
         给用户一个明确提示（比如"当前使用备用模型，响应可能较慢"），
         否则用户会以为系统卡死了。
       → 已落地（同日）：见 7.9。

    ⑥ 观察点⑤ 的补充认知（本次复验时纠正的一个判断错误）：
       我一开始用「ask() 是否抛 LLMNotConfiguredError」来判断，结果发现没抛，
       一度以为是缺陷。读代码后确认**这是正确的分层契约**：
         · LLMClient.chat()    —— 抛 LLMNotConfiguredError（基础设施层该抛就抛）
         · GameDataAgent.ask() —— 永不抛异常，一律转成 AgentAnswer(ok=False)
       ★ 原因写在 ask() 的 docstring 里：它是**前端的唯一入口**，
         一次失败不应该让整个页面崩掉。实测两层的表现都正确：
         客户端层异常文案完整（列出两个环境变量名 + 指向 .env.example），
         Agent 层返回 ok=False + 一段人话（"把 .env.example 复制为 .env 并填入 Key"）。
       ★ 教训：**验证"异常处理"时，先确认这一层该不该抛**。用错层的契约去断言，
         会把正确实现误判成缺陷 —— 这和第 21 条"测试要断言外部依赖没被触碰"
         是同一类问题：**断言的对象必须是设计契约，不是我的直觉**。

7.5 评测集扩充 v1.1（18 → 31 条）
--------------------------------------------------------------------------------
【为什么要扩】Phase 5 的 Q11 里我自己写过局限：「18 条用例只能覆盖主干路径，
    覆盖不了长尾问法」。运营的真实提问不会照着指标名念，这 13 条就是来补这个洞的。

【新增 8 条长尾问法（考"口语化提问扛不扛得住"）】
    E19  这几天活跃的人多吗            → dau（"活跃的人"不是指标名）
    E20  昨天 DAU 是多少               → dau + 单日窗口（@data_end-1）
    E21  七日留存掉了吗                → retention_rate + day_n=7
    E22  付费转化情况                  → payment_rate
    E23  平均每个用户能贡献多少钱       → arpu

           这两个指标分母不同（全体活跃用户 vs 仅付费用户），是最容易混的一对。

【新增 3 条多轮追问（考"指代与上下文继承"）】

7.6 ★ 评测器的第二次误报（v1.1 跑完才发现的）
--------------------------------------------------------------------------------
    现象：扩到 31 条后，数字可追溯率从 96.99% 掉到 92.28%，一次掉了近 5 个点。
    人工复核：掉下来的**全是真实来自数据库的数字** —— 模型在长尾问法下会主动
              多查 arppu / arpu 做交叉验证（E22 实际查了 payment_rate + arppu +
              arpu），那些数字有出处，却被判「找不到出处」。
    根因：对账集里只装「本用例期望指标」的真值切片，模型多查的指标不在里面。
          ★ 这和第 6.6 的缺陷 3 是同一个病根：**惩罚了"多查"，而不是"漏查"**。
            同一个坑我踩了两次，说明"评测指标设计"本身就是个独立的技能点。
    修复：runner 新增 build_extra_reference_values(actual_calls, exclude_metric_id)，
          用**模型自己声明的 metric_id + params 再走一次独立查询**，把实查指标的
          真值并入对账集；同时把实查到的参数值也加入 extra_allowed 白名单。
    结果：96.73%。

    ★ 必须说清楚的一件事（很可能在这里被追问"你是不是把标准放松了"）：
      这次放宽的是「**允许哪些指标参与对账**」，**没有放宽「数字必须来自数据库」**。
      判据仍然是「这个数能不能在库里查到」，而不是「模型说它对」。
      前者是覆盖面的问题，后者是标准的问题 —— 后者一旦松，整个评测就废了。
      这是刻意划清的一条线，也是第 6.3 节"双路径对账"能成立的前提。

    ★ 一个测试上的教训：新写的两个 runner 测试忘了传 agent=FakeAgent(...)，
      结果单测真的去调了大模型 —— 从 CaseResult 的 usage.total_tokens=7345
      才发现（单测消耗真实 token，而且结果不稳定）。
      依赖注入的测试，光断言"返回值对不对"不够，还要能断言
      「它没碰过真实外部依赖」。教训记在第九节第 21 条。

7.9 降级提示的产品化落地（复验遗留项②的收尾）
--------------------------------------------------------------------------------
【问题】复验发现备用链路延迟是主链路的 4~5 倍（12~18 秒 vs 3.4 秒）。
    系统"能答"但用户会以为卡死 —— 这是典型的**技术可用 ≠ 用户可感**。
    ★ 更实际的损失：用户以为卡住 → 点重试 → 白白多烧一次 token，
      而且这次大概率还是走备用模型，等于把降级的成本又放大一倍。

【做法】app.py 新增 fallback_notice(answer)，三处使用：
    ① 聊天区：回答来自备用模型时，先打一张 warning 牌再给结论
    ② 导出文本：追加一行「降级提示」
    ③ 判据取 cfg.LLM_PROVIDER_ORDER[0]，**不写死 "deepseek"** ——
       以后调整主备顺序时 UI 不用跟着改（配置即事实来源）

    ★ 为什么连导出文本也要带：导出的 txt 常被当成"分析记录"流转出去。
      事后有人追问「这条结论是谁算的、可不可信」时，**模型来源是关键信息**。
      只写在页面上，一旦导出就丢了 —— 审计信息必须跟着结论走。

【文案设计】不是简单说"已降级"，而是把两个真机发现直接告诉用户：
    · 响应明显更慢（4~5 倍）
    · 指令遵循能力较弱，出现过「不查库直接编数字」（已被来源校验拦下），
      请对结论中的数字多留一分核对
    ★ 产品判断：降级提示的价值不在"告知故障"，而在**调整用户的信任预期**。
      与其说"系统降级了"，不如说清"这次的结果你要多看两眼" ——
      这才是对用户真正有用的信息。

【验证】桩掉 streamlit 后直接调用（app.py 是 Streamlit 入口，模块级有
    st.set_page_config，不能直接 import），四个分支实测：
        主模型 deepseek        → None（不提示）                    ✓
        备用模型 glm           → 返回降级提示                       ✓
        以后新增的第三方 other → 返回降级提示（配置驱动，无需改代码）  ✓
        provider 为空          → None（未成功调用，不误报）          ✓
    导出文本：主模型不含「降级提示」，备用模型含                       ✓
    回归：py_compile 通过 + 395 个测试全绿                            ✓

八、真机验证记录（Phase 1~3，2026-09-18）

8.1 验证方法
--------------------------------------------------------------------------------
用 4 组问题覆盖 Agent 的 4 种典型表现，然后把 Agent 报出的每一个数字
拿去和数据库直查结果逐行比对。理由是：LLM 最容易出的问题是"看起来很对"，
必须用独立路径核对，不能只看它说得流畅就通过。

8.2 四组问题与结论
--------------------------------------------------------------------------------
【第 1 组】最近 7 天的日活怎么样？
    考察：单指标抽取 + 默认参数
    表现：2 轮迭代（第 1 轮同时调 get_metric_detail + query_metric，第 2 轮输出）
    结果：正确取到 7 天 DAU，并给出趋势判断 + 小样本提醒 + 主动追问下一步
    ★ 值得记录：同一个问题先后跑过两次，第一次是 3 轮迭代（两个工具分两轮调），
      第二次是 2 轮迭代（同一轮并发调）。路径不同，但结论和数字完全一致。
      这恰恰说明 Agent 的鲁棒性——它不依赖某条固定路径，只要目标达成即可。

【第 2 组】次留是多少
    考察：★ 别名映射能力（「次留」→ retention_rate + day_n=1）
    表现：正确映射。注意系统提示词里从没写过「次留 = day_n 1」，
          但 get_metric_detail 的参数说明里写了「用户说『次留』取 1」，
          模型是运行时去查才知道的 —— 这证明"口径知识放注册表"的路子走通了。

【第 3 组】v2.0.0 版本上线后新用户留存变好了吗？
    考察：多参数抽取 + 样本量提醒 + 人工确认节点
    表现：★ 在同一轮里并发调用了两次 query_metric（同时查 D1 和 D7）。
          这条路径之前只有单元测试覆盖，真机第一次就触发了，省了一轮 API 往返。
          回答中同时出现了三条硬性规则的落地：
            · 样本量提醒：「7 日口径的上线后批次只有 376 人，样本偏小」
            · 相关不等于因果：「留存变好不能直接等同于版本改动导致」
            · 人工确认节点：「以上建议需人工复核后执行」（提示词里的原话）

【第 4 组】去年 12 月的日活是多少？
    考察：★ 知识缺失时是否诚实
    表现：只有 1 轮迭代、一次工具都没调。模型直接从提示词的数据边界判断出
          这题超范围，回答「数据只覆盖 2026-06-20 ~ 2026-09-17」，
          并主动给出三个替代选项。
    意义：既没编造数字，也没浪费一次 API 调用。这是"知道自己的边界"的体现。

8.4 验证中发现的两个改进点（Phase 6 已全部落地）
--------------------------------------------------------------------------------
    ① Token 成本（实测精确值）：
         第 1 组（简单查询）      5,395 tokens / 2 轮
         第 2 组（别名映射）      8,001 tokens / 3 轮
         第 3 组（多指标对比）    8,773 tokens / 3 轮
         第 4 组（知识边界，0 工具调用）  2,316 tokens / 1 轮
       ★ 关键发现：第 4 组一次工具都没调，仍消耗 2,316 tokens —— 因为系统
         提示词里的 12 条指标目录是固定开销（每次请求都要带）。
       → 优化方向（Phase 6）：精简目录描述、或使用 prompt caching（命中缓存后
         这部分成本可降到约 1/10）。这是"Agent 产品的成本结构"这类问题
         的绝佳素材：固定 prompt 开销在小问题上占比可能超过 40%。
       → Phase 5 已把这笔账量化下来：全量 18 条平均 7,160.8 tokens / 2.67 轮，
         优化前后可以直接对比，而不是凭感觉说"好像快了点"。
       → ★ Phase 6 已做完：目录拆双形态 + 别名去重 + 删重复表头，同组 18 条
         平均降到 6,796.4 tokens（-5.1%）；再加缓存计量，实测命中率 90.69%。
         完整过程见 7.3。

    ② 主备降级未在真机验证：本次走的是 DeepSeek（主），降级到 GLM 的路径
       当时只有单元测试覆盖。验证方法：把 .env 里 DEEPSEEK_API_KEY 临时清空，
       再提问一次即可观察是否自动切换。
       → ★ Phase 6 已真机验证，5 个观察点全过（见 7.4 验证一）。
         而且这一步不只是"确认代码没写错"——它顺带爆出了本阶段最严重的缺陷：
         GLM-4-Flash 会跳过工具调用直接编数字，由此催生了第五层防线（7.4 验证二）。
       ★ 这件事的启发：**"只有单测覆盖"的功能，等于没验证过的功能。**
         因为单测只能证明"我实现的逻辑符合我的假设"，而真机验证才能推翻假设。

================================================================================
九、踩坑清单（按"会不会再犯"排序）
================================================================================

    1. 先建索引再导数据 → 慢 3~5 倍。正确顺序：导入 → 建索引。
    2. 真实数据不去重直接入库 → 16.9 万组重复主键让指标失真。
    3. 留存批次窗口不随 N 前移 → D7/D30 返回 NULL。
    4. 正则提取表名没设 SELECT/WITH 终止符 → 跨查询块误判。
    5. 默认日期写死绝对值 → 数据更新后默认口径就错了。改用 @data_end-N。
    6. 无脑重试所有异常 → 401 白等好几秒。要按 status_code 分类。
    7. 只在 SQL 执行前后判断耗时 → 慢查询照样卡死。必须用 progress handler。
    8. 让 LLM 自己把工具结果复述给前端画图 → 数字可能对不上。同一次查询
       同时产出文本和结构化两份数据。
    9. 工具一失败就抛异常中断循环 → 模型没机会自我修正。
   10. 图表数据只留在工具返回里、没往 AgentStep 上带 → 前端拿不到数，图静默不出。
       结构化数据要和文本一起沿调用链透传，并补测试断言它不丢。
   11. 把指标单位套到同一行的每个数值列上 → 「样本量 812%」这种错误表述。
       单位是"列"的属性，不是"结果"的属性。
   12. 渲染入口写统一的 `if not spec.y: return None` → 漏斗图（y 本就为空）
       被这道守卫直接杀掉，界面一片空白。守卫条件要确认对所有分支都成立。
   13. Streamlit 里把 Agent 写在脚本主体（不缓存）→ 每次交互重建客户端、
       每次重跑重新调 API，token 无声燃烧。资源用 cache_resource，
       结果存 session_state。
   14. 评测的真值参数没继承期望参数 → 拿默认窗口当真值，模型答对了反被判错。
       评测里最隐蔽的一类错误：**尺子量错了，还怪被测对象**。
   15. 评测指标用"对上/对不上"两档 → 把「均值 517」「530 左右」这类正确表达
       全判成编造，可追溯率凭空掉到 78%。**会误报的指标比没有指标更糟。**
   16. 参数判定只看最后一次调用 → 惩罚了"多查一个口径做对比"这种加分行为。
       评测要惩罚的是漏查，不是多查（和指标映射保持同一口径）。
   17. 数字抽取只认紧邻字符、只认 2026-09-11 格式的日期 → 「第 3 步」（带空格）
       和「09-05」（省略年份）被拆成数据值，制造假警报。规则要按**真实输出**
       去打磨，不能只按自己想象的输入写。
   18. ★ 以为"提示词写了禁止编造"就够了 → 备用模型跳过全部工具调用，直接编出
       「日活 100,000 人」。**四层 SQL 防线全在 SQL 出口，管不住"压根没去查"。**
       安全防线要沿数据流布置：提示词是软约束（请求模型配合），
       架构才是硬保证（保证系统正确）。→ 补第五层答案来源校验。
   19. ★ 版本号正则写成 [vV]?\d+(\.\d+)+ → 把 45.00 这种**小数**也当版本号剔掉了，
       而小数恰恰是这条防线最该抓的形态（留存率 42.66%、付费率 3.85%）。
       校验形同虚设却毫无报错。正确写法 [vV]\d+(\.\d+)+|\d+(\.\d+){2,}
       （要求带 v 前缀或至少两个点）。★ 教训：**正则的"误放行"不会报错，
       比"误拦截"更危险** —— 误拦截至少能被人看见。所以每写一条过滤规则，
       都要配一个"不该被它过滤掉"的反向用例。
   20. ★ 对账集只装"期望指标"的真值 → 模型多查指标做交叉验证的真实数字被判
       「找不到出处」，可追溯率从 96.99% 掉到 92.28%。**同一个坑踩了两次**
       （Phase 5 是参数判定只看最后一次调用，Phase 6 是对账集只认期望指标），
       病根都是"惩罚了多查"。修复时务必划清界限：可以放宽"哪些指标参与对账"
       （覆盖面），不能放宽"数字必须来自数据库"（标准）。
   21. ★ 单测忘了传 agent=FakeAgent(...) → 测试真的去调了大模型（从
       usage.total_tokens=7345 才发现），烧真实 token 且结果不稳定。
       **依赖注入的测试，光断言返回值不够，还要能断言"它没碰过真实外部依赖"。**
   22. ★ 复验备用链路时，用「ask() 会不会抛 LLMNotConfiguredError」当判据，
       结果没抛，一度误判成缺陷。实际是**分层契约**：LLMClient.chat() 该抛就抛，
       GameDataAgent.ask() 作为前端唯一入口永不抛、一律转 ok=False。
       **验证异常处理前，先确认"这一层该不该抛"** —— 拿错层的契约去断言，
       会把正确实现误判成 bug。断言的对象应该是设计契约，不是我的直觉。
