app.py —— Streamlit 前端主入口
--------------------------------------------------------------------------------
【体量】649 行（非空，总 781 行）/ 35.2 KB
【是什么】项目唯一的前端入口脚本，`streamlit run app.py` 即启动整个产品。
【作用】
  · 页面配置与示例问题（_EXAMPLE_QUESTIONS 四条真实运营问法）
  · 三级缓存：get_agent() / get_metric_registry() 用 st.cache_resource，
    get_table_stats() 用 st.cache_data(ttl=600)
  · 纯逻辑层（与渲染解耦、可读性最好的部分）：
      is_decision_analysis(answer)  —— 判断是否属「重大决策类」（模型自述 + 问题关键词双路径）
      fallback_notice(answer)       —— 备用模型降级提示（判据取 cfg.LLM_PROVIDER_ORDER[0]，不写死）
      build_history(turns, n)       —— 组装多轮追问历史（只取成功轮次、最多 2 轮）
      build_export_text(answer)     —— 把一次问答导出成纯文本（含执行过程与 SQL）
  · 渲染层：render_sidebar / render_turn / render_query_block /
    render_process_block / render_confirmation_block
  · ★ Phase 9：执行过程视图与导出文本各新增一个 `kind == "grounding"` 分支 ——
    渲染第五层防线的「来源校验标注」（几个数字中几个没找到出处）
【在架构中的位置】前端层（Phase 4）。调用 src.agent.GameDataAgent.ask()、
  src.ui.charts.*、src.ui.overview.load_table_stats()；被用户直接运行。
【设计要点】
  ① Agent 实例必须 st.cache_resource 缓存 —— Streamlit 每次交互都从头重跑脚本，
     不缓存就会每点一次按钮重建 LLM 客户端、重读注册表。
  ② 问答结果存 st.session_state 而非重问 —— LLM 按 token 计费，展开侧边栏也会触发重跑，
     存状态让「重跑 = 重新渲染」而不是「重新请求」。
  ③ 重大决策类结论强制走「复核人 + 勾选 + 写审计日志」——
     这是硬约束④在前端的落地，把「人工确认」做成产品形态而不是免责声明。
  ④ 清空对话不清审计日志 —— 审计数据一旦产生就不该被一键抹掉。
  ⑤ ★ 新增一种 step.kind 就必须同步改渲染分支 —— `kind="grounding"` 若不处理，
     会掉进「兜底工具调用」分支被渲染成乱码。渲染层与 trace 契约是一对：
     Agent 侧多写一种 kind，前端与导出文本两处都要跟着补。

.gitattributes —— 行尾符与文本属性规则
--------------------------------------------------------------------------------
【体量】22 行（非空，总 25 行）/ 1.0 KB
【是什么】Git 的「路径 → 属性」规则文件，统一仓库内的行尾符与二进制处理方式。
【作用】`* text=auto eol=lf` 让所有文本文件在仓库内一律存为 LF；
  对 .db / .db-shm / .db-wal / .xlsx / 图片显式标记 `binary`（禁止行尾转换与 diff）；
  对 .bat / .cmd 保留 CRLF（否则可能无法执行）。
【在架构中的位置】工程配置，无代码依赖；作用于 Git 层面而非运行时。
【设计要点】加它的直接动因是**消除跨平台的假 diff**：
  Windows 上默认 CRLF，若不统一，同一份文件在不同机器上会被 Git 判成
  「整个文件都改了」——真正的改动淹没在噪声里，Code Review 也会失真。
  ★ 另一个收益是防损坏：显式声明 `binary` 能阻止 Git 对 .db 做行尾转换，
    二进制文件被转换会直接损坏。
  ★ 它是「仓库交付化」这一步的产物：**代码能跑 ≠ 仓库能协作**，
    行尾符这类问题只在「别人 clone 下来」时才暴露。

src/grounding.py —— 答案数字溯源原语（Phase 9）

【是什么】第五层防线的判据原语：把答案里**每一个数字**反向映射到本次查询的结果集。

  · 二、数字比对：_REL_TOLERANCE 0.5% / _LOOSE_TOLERANCE 3% / _ABS_TOLERANCE 0.05、

  与 src/eval/metrics.py（评测台），两者都从本模块 import —— 口径只有一份。
  本模块**不 import src.agent、不 import src.eval**，也不依赖 LLM 与真值。
【设计要点】
  ① ★ **下沉是为了解除真实的循环导入，不是风格洁癖** —— 依赖方向是 eval → agent
     （runner.py 要 import AgentAnswer、judge.py 要 import LLMClient），
     而 src/eval/__init__.py 又会 import runner。若 react_agent 直接 import
     src.eval.metrics，则「app.py 先导入 react_agent」这条路径会在包初始化中途
     去取尚未定义的 AgentAnswer → ImportError。把共用原语放到谁都不属于的
     中立模块，是唯一能让两边都干净复用的解法。
  ② **口径必须只有一份** —— 运行时防线和评测台各写一套数字正则，迟早会出现
     「线上拦了、评测说没问题」这种自相矛盾的结论。测试用
     `src.eval.metrics.extract_numbers is src.grounding.extract_numbers`
     这条同一性断言把两边的口径钉死。
  ③ **鸭子类型而非 import 类型** —— 读执行轨迹只认 kind / tool_name / ok / result
     四个属性，因此既能喂 AgentStep 对象，也能喂它序列化后的字典。
     和「指标语义层不 import 数据层」是同一个思路：靠约定，不靠 import 耦合。
  ④ ★ **日期规则里的 2025-12 是被拒答用例当场抓出来的** —— 少了「年-月」这条，
     `\d{1,2}-\d{1,2}` 会从中间把 2025-12 咬成 25-12，残留一个 20 被当成数据值，
     于是一条**正确的超范围拒答**反而被判成「编造」而拦截。
     旧实现用 `\d{3,}` 天然挡住两位数字，换成通用 extract_numbers 后这层隐形保护消失。
  ⑤ **阈值是常量而非自适应校准** —— 1/3 写死在模块里，拒绝「根据历史数据自动调」。
     因为判据一旦会自己漂移，就无法复现「上次为什么拦了这条」。

--------------------------------------------------------------------------------
【体量】654 行 / ~33 KB（非空）
【是什么】把用户上传的 CSV 解码 → 推断列类型 → 生成建表 DDL → 导数的完整流水线，
  让用户能把新数据当场喂进系统。
【作用】
  · decode_csv(raw_bytes)        按 BOM/编码探测顺序解码 CSV 字节流

  · infer_date_columns(df)       日期列识别两道门：列名关键词 + 列值采样解析，
                                 format="mixed" 支持混合日期格式
  · normalize_identifier(name)   列名→合法 SQLite 标识符（中文/特殊字符转义）
  · generate_ddl(table, df, types)  按 DataFrame 列与推断类型生成 CREATE TABLE
  · load_csv_to_sqlite(...)      建表 + 导数 + 建索引，返回 UploadResult

  ⑤ DTO 键名与 dataset.py 的 summary["tables"] 用 "name" 分开 ——
    UploadResult.to_dict 用 "table_name"（数据层语义更准），单测有键名回归锁。

  ① 为什么手搓不用 LangChain —— 本项目硬约束是「LLM 绝不能写 SQL」，
     而 LangChain 的 SQLDatabaseChain 恰恰让模型直接产 SQL，用它等于把核心安全设计交给框架。

     GLM-4-Flash 实测跳过全部工具直接答「日活是 100,000 人」，四层防线完全无感。
     ★ Phase 9 把判据从「一次都没取数 + 有数字」升级为**逐数字溯源**：
       旧判据只要有一次成功取数就整条放行，于是「查了 1 次 DAU、又编了 5 个留存率」
       能大摇大摆过去。新判据把答案里每个数字反向映射到本次结果集，按无出处占比
       分三档：pass（全都有出处）/ annotate（≤1/3，回答照给 + 末尾标注）/
       block（>1/3，不把数字给用户看）。

     以及推导池没覆盖的表达（加权、中位数）都会被归到「找不到出处」，
     一律拦截会因为一个近似值废掉一整段正确推理，过度拦截的代价是用户再也不信这个提示。
     向后兼容：一次成功取数都没有时参考集为空 → 占比 1.0 → block，与旧判据完全一致，
     所以新判据是旧判据的**严格超集**。
     判定原语来自 src/grounding.py（与评测台共用同一份口径），
     必须绕开日期与版本号，否则正确的拒答（含 2026-06-20）会被误判。
     grounded_calls 仍保留，但不再直接决定拦截，只作诊断信息 ——
     用来区分「压根没查」和「查了但混编」这两种不同的失败。
     补救用尽仍编造 → 拦截整条回答（硬约束⑤）。

【设计要点】
  ① ★ **判据必须锁死在真值上** —— 若允许评审员用外部知识判断，它会退化成「常识裁判」：
     看到「次留 42%」觉得合理就通过，哪怕真值里根本没这个数。
     这是本项目「防自证」的第二重保险（第一重是 runner.build_reference 走独立路径）。
  ② **一次调用同时拿回句子核验与四项打分** —— 两者读的是同一份上下文，

     用 LLM-as-a-Judge 替代 + 真值独立路径堵住自证风险，在这个规模下性价比更高。
     **这是有意识的取舍，不是没考虑过。**
  ④ ★ **软约束会被违反，所以要补硬校验** —— Phase 5 的 A 轮出现过一次自相矛盾：

     于是解析层加一致性守卫。两个关键设计：
     **留痕而非静默改判**（否则报告「看起来更准了但没人知道被改过」，等同篡改数据）、
     **单独统计 consistency_fixed**（大于 0 说明硬要求仍被违反、只是被兜住了 ——
     兜住不等于消失，下一轮该盯的是这个数归零）。

【体量】144 行 / 7.8 KB
【是什么】命令行跑评测并输出报告，支持 --limit / --cases / --out / --no-report / --dump。
【作用】
  · print_progress：实时进度（把映射/参数/数字三个结果都打出来，
    真机跑一条要十几秒，边跑边看才能第一条就发现 prompt 是否写崩）
  · main()：加载评测集 → 过滤用例 → 跑全量 → 终端总览 → 报告落盘
    （默认 docs/03_评测报告/评测报告_Phase6.txt）→ 可选 --dump 结构化 JSON
【在架构中的位置】评测体系入口脚本。依赖 src.eval 全部模块与 src.config。
【设计要点】
  ① 默认落盘报告 —— 评测的价值在于可对比，只打印到终端关掉窗口就没了，
     下次只能凭印象说「好像变好了」。
  ② --limit / --cases 是开发期省钱纪律 —— 真机跑一条几千 token，先跑 2~3 条验证流程。
  ③ --dump 存模型原话 —— 报告只写「存疑数字：25」，人复核需要看上下文才能判断
     是编造还是合理表达，存下来才能离线复查（重跑一次要烧十几万 token）。
  ④ encoding="utf-8" 必须写 —— Windows 默认 GBK，报告里有中文和 ✓ ✗ 会直接报错。

scripts/run_tool_eval.py —— 工具调用准确性专项（Phase 1 · 维度一）
--------------------------------------------------------------------------------
【体量】444 行（非空）/ 22.6 KB
【是什么】回答**更上游的问题**：工具调对了吗（端到端只告诉你「答错了」，
  不告诉你错在选指标、抽参数，还是答对了却编数字）。
【作用】
  · 按 MultiCAT-Bench 的六类错误分级：GE 生成错误 / NCA 完全未调用 /
    NNC 无需调用却调用 / WNC 调用数量错误 / WTC 调用了错误工具 / WA 参数错误
  · 分级优先级 WTC > WA > WNC > OK —— 先判「选错指标」再判「参数错」最后判「次数异常」，
    因为选错指标是最严重的错，不该被后面的标签掩盖
  · 产出 F1（把「是否需要调用工具」当二分类问题）、错误分布、badcase 明细
【在架构中的位置】评测体系入口脚本。依赖 src.eval（复用 check_metric_mapping /
  check_params / metric_calls）与 src.agent。
【设计要点】
  ① **不另起一套标准** —— 指标/参数判定直接复用 eval 层的函数。
     两套尺子量同一件事，迟早会打架（这正是 Phase 3 踩过的「两把尺子」）。
  ② **为什么用 F1 而不是准确率** —— 「漏调」和「误调」代价不同：
     漏了等于答非所问，误调等于白花一次 LLM 往返 + 一次 SQL 查询。
     准确率会把两类错误混成一个数，看不出该往哪边优化。
  ③ 顺带把 SQL 安全防线也验了 —— 从**用户问题**这条真实攻击路径出发，
     用恶意参数（而非恶意 SQL）打，因为架构上 LLM 根本写不了 SQL。

scripts/run_perf_eval.py —— 缓存命中率 + 响应性能专项（Phase 2 · 维度二/五）
--------------------------------------------------------------------------------
【体量】326 行（非空）/ 17.9 KB
【是什么】回答「快不快、贵不贵」—— 这是产品能不能上线的问题。
【作用】
  · 拦截 LLM 客户端的 chat 方法，按**单次调用**记录 usage 与耗时
  · 端到端耗时拆解（LLM 往返 vs SQL 执行）、P50 / P90 分位
  · 缓存命中率 = 命中 token / 输入 token
【在架构中的位置】评测体系入口脚本。依赖 src.agent.llm_client 与 src.eval。
【设计要点】
  ① **为什么把缓存和性能放一起** —— 两者共享同一个根因：ReAct 循环每多走一轮，
     就把「系统提示词 + 历史」整包重发一次。轮次既推高延迟又推高成本，
     而前缀能不能被缓存命中，直接决定这部分重复开销按全价还是 1/10 计价。
  ② **为什么用 monkey patch 拦截而不改生产代码** —— 生产代码里 usage 是
     按一次问答累计的，累计后就分不清哪一次命中。而「缓存利用率」必须按单次调用
     统计才有意义。★ 姿态很重要：**为了测量而改被测对象，测出来的就不是它了。**
  ③ **缓存命中率的分母是输入 token** —— 缓存只作用于输入侧，
     用总 token 当分母会把输出摊进来稀释命中率。
  ④ 局限要主动写出来：GLM 不返回缓存字段（cached_tokens 恒为 0），
     所以本维度**只能测主供应商 DeepSeek**。

scripts/run_robustness_eval.py —— 鲁棒性与边界专项（Phase 4 · 维度六）
--------------------------------------------------------------------------------
【体量】651 行（非空）/ 34.4 KB
【是什么】测**模型在「不该正常回答」的时候，会不会乱答**。
【作用】
  · 21 条用例分五类：歧义 / 知识缺失 / 恶意输入 / 领域外 / 超长异常输入
  · 六类行为断言（该反问的有没有反问、该拒绝的有没有拒绝、有没有静默失败）
  · 数据库快照核对（跑完后库完好）+ **第五层防线触发计量**（guard_count）
【在架构中的位置】评测体系入口脚本。依赖 src.eval.robustness_cases.json 与 src.agent。
【设计要点】
  ① **判据是 0/1 行为断言而不是打分** —— 这四类场景的正确答案是唯一的
     （歧义就该反问、没有的指标就该说不支持），既然唯一解，打分只会引入主观性；
     而且**不需要再花一次 Judge 的钱**（实测 4,549 token/条，比 Phase 3 的 7,053 便宜）。
  ② ★ **代理指标的局限要主动写出来** —— 断言依赖「信号词表」「问号检测」，
     它们是近似而非判定（实测 R02 的「没有明显掉量」误命中了拒绝信号词「没有」）。
     所以报告把原始回答完整留档，并标注「异常项必须人工复核」。
     **把判据的局限写出来，比假装它精确要诚实得多。**
  ③ ★ **「隐身」的防线要专门计量** —— 第五层防线的工作是「发现无出处数字 →
     拦掉 → 要求模型改口」，被拦掉的内容不会留在最终回答里，
     所以「最终回答没问题」既可能是没触发、也可能是触发并修好了。
     于是单独统计触发次数（实测触发 1 次），把隐身的动作变成可观察的数据。
  ④ ★ Phase 9：抽数字改为调用 src/grounding.extract_numbers ——
     也就是运行时防线自己用的那一份实现。评测台不再自己维护一套正则，
     从源头杜绝「线上判据和评测判据不一致」这类假警报（同源比对的意义就在这里）。

  程序（或 Excel）读 csv/json 复核证据。平铺在一起时，评测每跑一轮就多几个文件，
  几十个之后「找一份报告」变成体力活；更要紧的是**结论与证据混层** ——
  看报告的人不知道去哪里复核，要复核的人不知道结论在哪。
★ 目录常量统一定义在 src/config.py 的 DOCS_*_DIR，5 个评测脚本只引用常量、
  不自己拼路径字符串 —— 将来再挪位置只改一处（「配置与代码分离」的延续）。
它们是「作品集的证据链」——证明的不只是代码能跑，还有「作者知道自己在做什么」。
★ 留档纪律（v1.5/v1.6 立的规矩）：**评测输出直接写进 docs/ 并带轮次标识**，
不要先落到仓库根目录的 `_tmp_*.log` 再「回头整理」——**「回头整理」约等于「永远不整理」。**

【在架构中的位置】文档层，是测试侧的主文档，与《开发复盘记录_Phase1-3.txt》配套：
  前者答「怎么一步步做出来的、为什么这么设计」，本文档答「怎么证明它真的能用」。
【设计要点】
  ① ★ **与开发复盘记录同一条维护约定** —— 每个 Phase 完成后**整份覆写**，
     不做「打补丁式追加」；前面的结论被后面的测试推翻时**直接改写前面的段落**
     并注明修订，保证从头顺读时逻辑自洽。目标：可顺读、可整份丢给 AI 分析、
     可自留复盘与技术沉淀。
  ② ★ **把「评测台自身缺陷」和「被测对象缺陷」分开记** —— 这是本文档最独特的
     一条约定。到 Phase 5 为止，评测台自身出错 5 次，而被测对象只有 1 类真实缺陷。
     这个比例本身就是结论：**评测台比被测对象更容易出错，因为它没有人在盯着。**
     如果分不清这两类，就会去「优化」一个本来没问题的模型 —— 越优化越糟。
  ③ ★ **连「没出错」的测量本身也会波动** —— Phase 5 发现同一份提示词、同一天、
     同一批用例跑两轮，无依据声明率是 2.29% 和 4.37%。所以本文档里所有
     「降了多少」的说法都要先问一句「对照组自己稳不稳」——单次差值不构成证据。
  ④ 全文中文、表格化，关键结论带 ★ 标记，是上手前唯一需要通读的一份。

     被拦掉的内容不会留在最终回答里，所以「最终回答没问题」既可能是没触发、
     也可能是触发并修好了。不单独计量，就无法证明它真的在工作（实测触发 1 次）。

13.3 一句话记住这个项目
--------------------------------------------------------------------------------
  它用「指标语义层」把 LLM 的职责收窄成「分类 + 抽参」，用「四层 SQL 防线 +
  第五层答案来源校验」保证每个数字都能溯源，再用「双路径对账评测」把
  「好像挺好用」变成可量化、可对比、可归因的数字。

  读代码时抓住一条主线就不会迷路：
      用户提问 → agent/react_agent.ask()
               → agent/tools.query_metric()
               → metrics/registry + sqlgen/generator 生成 SQL
               → sqlgen/validator 校验 → sqlgen/executor 执行
               → 结果双份返回（content 给模型 / data 给前端）
               → ui/charts 自动出图 + app.py 展示与人工确认
               → eval/runner 事后对账
